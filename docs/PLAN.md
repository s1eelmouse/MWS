## 4. Даты, каталог и состояния — главный приоритет

- [x] Модель отдаёт временное выражение как в тексте, код вычисляет дату от `started_at` («вчера», «со вторника», «после двух», «через неделю»). Режим `task` включён по умолчанию: на `4090-continue-002` полный val даёт `temporal_recall` 0.3566 → **0.4237** (пакет с сериями) или 0.4000 на один звонок; `state_accuracy` 0.3852, precision/recall/grounding не меняются. Детали — [DETERMINISTIC.md](DETERMINISTIC.md).
- [x] Календарь и детерминированная постобработка (`feat/temporal-normalization`): прежний `conservative` дал 0.3315 → 0.3398 и оставлен как отдельный режим; новый `task` закрывает отсечение на основной модели.
- [x] Удалять только точные дубликаты: на старом полном val это 102 факта из 1956 (90 — `agreement`), precision 0.3466 → 0.3657 без изменения recall, дат, состояний и grounding. Счётчик — `exact_duplicates_removed`.
- [x] Разобрать остальные `agreement`: у `continue-003` 138 совпало, 809 лишних, 340 пропущено. Основные классы лишних — actor-пересказы («клиент подтвердил…»), слабая/нулевая лексическая поддержка и длинные свободные формулировки; разбор — [RESULTS.md](RESULTS.md), раздел 5. Кандидат precision-режима (`actor + support<0.5`) даёт P 0.4149 → 0.5017 при T −0.0006, но по умолчанию не включён.
- [x] Проверено: длинные `agreement` (>8 токенов) дают precision 0.04; фильтр по длине улучшил бы precision, но ухудшил temporal и является удалением трудных фактов. Не включаем.
- [x] Сопоставление значений с `catalog.json`: точная нормализация меняет 3 поля на полном val и **не меняет официальные метрики**. Разговорные алиасы не включаем: это склеивает разные объекты до извлечения.
- [x] Словарь отрицаний: в train 199 отрицательных фактов из 18 475 (1,1 %), модель предсказывает 4; все 763 совпавших факта положительные. Массовое правило «есть „не“ → polarity=-1» противоречит контракту («перезагрузил — не помогло» — действие), поэтому не включено.
- [x] Ловушки: среди лишних `agreement` 15–17 содержат «возможно/если/может»; их удаление даёт P +0.003 без изменения T/S, но по умолчанию фильтр не включён, чтобы не удалять подтверждённые трудные формулировки.
- [x] Проверено закрытие `valid_to` у одно-значных атрибутов на сохранённом val: `temporal_recall` 0.3348 → 0.3289, `state_accuracy` 0.3339 → 0.3307. Правило ухудшает обе метрики и в код не включено.
- [x] Проверка существования `turn_idx`, допустимости дат и структуры фактов: `schema.source_problems`, `sanitize_interval` и `Facts.model_validate`; тесты `test_case_schema`, `test_prediction_normalization`, `test_temporal_task`. Невалидный источник отбрасывает только свой факт, если остальные валидны.
- [x] Проверено исправление источника по пересечению слов значения и реплики: на val +13 in-sample, но на двух половинах только +3 и +5 при 6 и 1 поломках. Правило нестабильно и в код не включено.
- [ ] Сократить формат ответа (короткие ключи, без пустых полей): эталонный ответ в train — медиана 409 токенов, и длина ответа — основная задержка. Меняется вместе с обучением, после смены нужно переобучать.

## Что отложено

MCP/агент, графовая база, массовая разметка учителем и оптимизация vLLM не входят
в обязательный проход. Возвращаемся к ним только после этапов 2–5.
Разметка учителем не нужна: данные уже размечены организаторами.
