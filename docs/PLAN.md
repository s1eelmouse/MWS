# План адаптации к выданному кейсу

Статус: план, а не описание уже реализованного поведения. Обновление 13.11.2026.

## 1. Согласовать контракт и спорные правила

- [ ] Уточнить у ментора допуск Qwen3-1.7B, официальный оценщик, неизвестные даты, правила value и источников.
- [ ] Описать вход звонка с call_id, started_at и turns; определить разрешённые метаданные.
- [ ] Описать факт и ответ со списком фактов, а также формат ошибок.
- [ ] Подготовить несколько небольших примеров нового формата: подтверждение, отказ, изменение состояния, относительная дата.

Готово, когда команда использует один согласованный пример запроса и ответа. Пример не подменяет будущий официальный HTTP-контракт.

## 2. Получить проверяемый проход без обучения

- [ ] Адаптировать schema.py, построение запроса, predict.py и формат экспорта.
- [ ] Сохранять call_id; исключить эталонные facts из входа модели.
- [ ] Удалить безусловное обрезание первых 3 000 символов. Измерить длины входов и ответов в токенах.
- [ ] Подключить исходный case_metrics.py; сохранять его версию/контрольную сумму.
- [ ] Получить предсказания готовой 0.6B на небольшом наборе, проверить факты и источники вручную.

Готово, когда полный звонок проходит через модель и экспортируется в официальный формат. Ошибки генерации видны в отчёте; это ещё не означает достаточное качество.

## 3. Адаптировать существующее обучение

- [ ] Переписать чтение данных и преобразование эталонов в train.py.
- [ ] Подобрать ограничение контекста по измеренным токенам входа вместе с ответом.
- [ ] Задать seed до создания модели/адаптера.
- [ ] Сохранять параметры модели и LoRA, prompt/schema, версии, происхождение данных и результаты отдельно для каждого запуска.
- [ ] Добавить промежуточное сохранение и возможность возобновления.
- [ ] Проверить оптимизацию logits_to_keep на новых примерах относительно обычного вычисления loss.
- [ ] Провести короткое обучение, проверить сохранение/merge/генерацию, затем запускать полный train.

Готово, когда запуск воспроизводим по сохранённой конфигурации, а качество проверено генерацией, не только validation loss.

## 4. Добавить даты, каталог и состояния

- [ ] Вычислять относительные даты от started_at по согласованным правилам.
- [ ] Разделять нормализованные значения и дословные источники.
- [ ] Связывать предложения с подтверждениями и учитывать область отрицания.
- [ ] Обновлять состояния по объекту и атрибуту, закрывая прежние интервалы.
- [ ] Проверять существование исходных turn_idx, допустимость дат и структуру фактов.

Готово, когда на контрольных примерах проверены смысл, даты, источники и текущие состояния; эффект каждого компонента измерен отдельно.

## 5. Проверить качество и принять решение о размере

- [ ] Прогнать полный val и сохранить предсказания с call_id.
- [ ] Разобрать пропуски, лишние факты, ошибки объекта, полярности, даты, состояния и источника.
- [ ] Сделать дополнительную проверку устойчивости к шуму, сохранив исходный val неизменным.
- [ ] При систематических ошибках понимания сравнить 1.7B с 0.6B при сопоставимых условиях, если модель разрешена.

Готово, когда выбор модели объясняется качеством и ресурсами. Обрезанный вход или неправильная схема не являются основанием увеличивать модель.

## 6. Подготовить сервис, измерения и сдачу

- [ ] Обновить контракт FastAPI и обработку ошибок; ограничить очередь/ожидание.
- [ ] Добавить Dockerfile и проверить запуск по инструкции в чистом окружении.
- [ ] Подготовить CPU-режим; измерить CPU/GPU по согласованной методике.
- [ ] Записать оборудование, batch size, длины входа/ответа, прогрев, задержку, throughput и пиковую память.
- [ ] Подготовить три измеренные точки «ресурсы × качество» и сравнение с baseline.
- [ ] Подготовить демонстрацию, резервное видео и презентацию с ограничениями решения.

## Что отложено

MCP/агент, сложная графовая база, массовая разметка учителем и оптимизация vLLM не входят в первый обязательный проход. Вернуться к ним после готовности данных, оценки и обучения.
