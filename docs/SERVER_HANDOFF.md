# Передача контекста команде: сервер, модели, XGrammar и даты

Документация отдельных тренировок: [experiments/README.md](experiments/README.md).

Состояние на 14 ноября 2026 года. Этот документ описывает фактически выполненные
эксперименты и следующие задачи. Сведения из отдельных прогонов не заменяют оценку
на полном val. Приватный SSH-ключ передаётся владельцем отдельно; его содержимого здесь нет.

## 1. Цель и текущий приоритет

Кейс МТС MWS CompactFactExtraction, хакатон «Инноглобалхак».
Из русскоязычного диалога поддержки нужно извлечь факты об услуге, устройстве,
тарифе, заявке, действии и договорённости, включая полярность, даты и реплику-источник.

Сейчас используем Qwen/Qwen3-0.6B, не 1.7B. Выполнены два цикла QLoRA.
Главные задачи на эту смену:

1. Подключить ограничение структуры генерации через XGrammar.
2. Измерить эффект на обеих сохранённых моделях одинаковым способом.
3. Разобрать и улучшить относительные даты и переходы состояний.
4. После выбора работающей версии получить три ресурсные точки, включая CPU.

Дополнительное обучение пока не запускать автоматически: второй цикл уже проверен,
а основной обнаруженный сбой сейчас — формат самостоятельной генерации.

## 7. Контракт, который нельзя случайно поменять

Источник истины — `src/schema.py`, классы Facts/Fact/CallInput.
Вход: call_id, started_at, turns с idx, speaker, text; есть дополнительные метаданные.
Gold facts не входят в запрос к модели; использовать `as_call`/`build_messages`.

Выход:

```json
{"facts":[{"object":{"name":"домашний интернет","type":"service"},"attribute":"service_state","value":"обрывы связи","polarity":1,"valid_from":null,"valid_to":null,"source":{"turn_idx":7}}]}
```

- attribute: service_state, tariff, ticket_status, action, agreement.
- object.type: service, device, ticket, client, other; поле необязательно.
- speaker при наличии: client или operator, должен согласовываться с source.
- polarity: целое -1 либо 1.
- valid_from и valid_to обязательны как поля, но допускают null.
- Даты ISO, реальные календарные даты, окончание не раньше начала.
- source.turn_idx — исходный idx реплики, а не её порядковая позиция.
- Лишние поля запрещены. Обёртка `{"fact": ...}` не предусмотрена.

Thinking выключен через chat template. Генерация greedy, sampling выключен.
Инференс merged-моделей на GPU — FP16. Обучение — QLoRA 4-bit NF4 + double quant,
compute BF16. Это разные режимы хранения/вычисления.

Подпись контракта обеих моделей:
`3ee403f3b8645663828a1208bd93e81a087b234afeb566c7c36882da63c4a274`.
Не менять SYSTEM/схему/целевой формат молча: check_model_contract обнаруживает смену.
Использовать --with-schema для обхода контроля совместимости не следует.

## 10. Найденные причины отказов

Первый диагностический повтор 22 звонков: 15 JSON syntax, 7 schema.
Во всех 15 — обёртка fact и нарушенная вложенность; один также смешивает поля:
`"attribute":"service_state":"слабый сигнал","value":"вай-фай"`.
После чтения целых фактов в четырёх ответах обнаружены конфликты speaker с source.

В семи schema-отказах — пять звонков с 2026-02-29 (10 полей), один обратный
интервал и один object.type=tariff. У последнего есть также обратные интервалы,
которые не были показаны до прохождения проверки типа объекта.

Вторая модель: 344 syntax-отказа, 3 schema; 346 отказов содержат обёртку fact.
Главный приоритет — структура генерации. Новая модель пока не заменяет первую.

## 11. Задача XGrammar

XGrammar поддерживает Qwen, Linux/NVIDIA и прямое подключение к Transformers
через logits_processor. Переобучение и переход на vLLM ради этого не обязательны.
Совместимость именно установленных у нас версий нужно подтвердить прогоном.

Официальные источники:
- https://github.com/mlc-ai/xgrammar
- https://github.com/mlc-ai/xgrammar/blob/main/docs/start/quick_start.md
- https://github.com/mlc-ai/xgrammar/blob/main/docs/start/workflow_of_xgrammar.md

Места подключения: Extractor.__init__ и Extractor._extract_batch в src/extractor.py.
Использовать JSON Schema из Facts.model_json_schema(), а не просто встроенную
грамматику любого JSON: последняя разрешит неправильную, но синтаксически валидную обёртку.

Детали реализации:
- Скомпилированную грамматику можно кешировать для данного tokenizer/schema.
- Размер словаря брать из model.config.vocab_size, не предполагать равенство len(tokenizer).
- Состояние matcher/logits processor должно соответствовать конкретной генерации
  и каждой последовательности batch; не переносить уже использованное состояние на следующий вызов.
- Thinking оставить выключенным. Не менять prompt одновременно с первым тестом
  XGrammar: иначе смешаются два воздействия.
- Начать с batch1, проверить batch2 и последний неполный batch, EOS и лимит ответа.
  В benchmark уменьшение batch при OOM запрещено; обычный extractor имеет рекурсивный fallback.
- Сделать явный флаг включения XGrammar и записывать его/версию пакета/схему в отчёт.
  Не смешивать constrained и unconstrained прогоны в одной неразличимой конфигурации.
- Custom Pydantic validators не превращаются автоматически в ограничения JSON Schema.
  Реальность календарной даты, порядок границ и source/роль обязательно проверять после генерации.
- Конец по лимиту токенов может оставить незавершённую структуру даже при ограниченном декодировании.
- XGrammar не гарантирует правильность фактов и источников; оценивать все метрики, не только valid rate.

Перед установкой зафиксировать текущее окружение:

```bash
python -m pip freeze > out/environment-before-xgrammar-001.txt
python -m pip install --dry-run xgrammar
```

Посмотреть план установки. Если требует замены рабочего torch/transformers,
лучше отдельное окружение, а не слепое обновление общего .venv.
После согласованной установки записать версии и выполнить pip check.

## 12. Задача дат

2026 год не високосный. Но замена 29 февраля на 28 не решает все случаи:
в звонке 22 марта модель тоже выдаёт февраль вместо мартовских переходов.
И обратный интервал нельзя чинить перестановкой границ.

Направление: выделять временное выражение и источник, считать дату от started_at
кодом, отдельно представлять неизвестность и переходы состояний.
Если для этого меняется обучающий target — новая версия контракта и отдельный адаптер.
Правила не должны зависеть от call_id или подсматривать в gold.
Где дата не выводится из текста, не придумывать точность ради похожести на эталон.

## 13. Как измерять изменения

После правки сначала тесты и небольшой срез:

```bash
python -m unittest discover -s tests -v
python -m compileall -q src tests
python -u src/benchmark.py --model out/merged-4090-continue-002 \
  --device cuda --batch-size 1 --limit 20 --output-dir out/xgrammar-preview-001
```

В эту команду нужно добавить фактически реализованный ребятами флаг XGrammar;
сейчас такого флага в исходном коде нет. Одна установка пакета его не включает.
Аналогично проверить первую модель, использовать отдельные output-dir.
После успешного smoke убрать --limit, batch2 проверять отдельным прогоном.
Не делать вывод о полном val по 20 звонкам и не выбирать только удачные случаи.

Для пересчёта сохранённых предсказаний без генерации:

```bash
python src/eval.py --gold data/organizer/val.jsonl \
  --pred out/benchmark-4090-continue-002/predictions.jsonl \
  --json out/recomputed-continue-002-001.json \
  --errors out/recomputed-continue-002-001-errors.jsonl
```

benchmark сохраняет report/environment/metrics, predictions/calls/batches/failures,
memory.csv. Raw есть у отказов; для анализа корректного, но неверного по смыслу ответа
смотреть predictions.jsonl и исходный диалог. Длины/причины остановки смотреть в calls.
Для XGrammar сохранять raw также при необходимости разбирать неверные допустимые ответы.

run_experiment.py может обучать, делать merge и три benchmark. Для готовой модели
использовать --model; --train-new требуется только для нового обучения.
Три режима по умолчанию: cuda:1, cuda:4, cpu:1. Полный CPU-прогон может быть долгим;
сначала пилот на том же небольшом срезе. Сравнивать одинаковые данные/порядок/лимиты/прогрев.
Проверка совместимости compare_runs не контролирует автоматически будущий флаг XGrammar,
пока его явно не добавят в протокол/набор параметров сравнения.

## 14. Критерии и ограничения оценивания

Пересчитанный baseline: precision .2189, recall .2488, temporal .4205,
state .3194, grounding .6906. Опубликованный отчёт имеет другие temporal .4161
и state .3483; источник порогов ещё нужно уточнить у ментора.

Отсечение temporal при падении более .05:
- по опубликованной базе нижняя граница .3661;
- по пересчитанной — .3705.
Цель потери не более .02: соответственно .3961 или .4005.
Наша исследовательская .3653 пока ниже обеих границ отсечения.

Нужны также корректная схема на 100% примеров, воспроизводимость, CPU/GPU-ресурсы
по единой методике, >=3 точки, разбор ошибок, устойчивость к шуму, Docker/HTTP и демо.
Схема пустого ответа может быть валидна, но полнота при этом нулевая: не подменять качество форматом.

Официальный оценщик src/official_case_metrics.py не менять, SHA256:
dffec9b8b20c5a8a101a33a27b1672f2b6195f00ab60f021a1c14b31eeeacabd.
Известны недостатки сопоставления объектов и текущего состояния. Temporal/grounding
считаются среди сопоставленных фактов, даты сравниваются по дню.
Baseline содержит 34 строгих schema-отказа, но их читаемые факты остаются в официальном
подсчёте; наши явные отказы экспортируются пустыми. Это оговорка сравнения.

GPU-секунды benchmark — выделенная одна GPU × время локальной обработки,
не сумма времени ядер; загрузка, прогрев, сеть и очередь исключены.
Память — пики PyTorch и выборки RSS процесса; память драйвера/пики загрузки не покрыты.
