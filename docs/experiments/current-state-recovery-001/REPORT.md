## Что изменено

### Тарифы: `src/tariff_recovery.py`

- Нормализация известного названия из каталога внутри служебной фразы.
  Учитываются знак `+`, наиболее длинное название и ограниченные падежные
  формы прилагательных; произвольного нечёткого слияния брендов нет.
- Извлечение явно названного текущего тарифа. Вопрос требует подтверждения;
  предложение перейти в будущем не становится текущим тарифом.
- Закрытие прежнего тарифа допускается только при явном указании, что он старый.
  При неподтверждённом конфликте существующее состояние сохраняется.
- Клиент должен однозначно определяться по уже извлечённым объектам.

### Услуги и устройства: `src/service_recovery.py`

- Восстановление пропущенного состояния явно названного объекта с опорой на
  каталог и уже извлечённые объекты. Эталонные факты не используются.
- Разделение симптомов, текущего состояния, вопросов, гипотез и будущих действий.
  Например, существительное «подключения» не означает «подключён».
- Защита от переноса неисправности между телевизором, телевидением и приставкой.
  При неоднозначном объекте правило воздерживается от добавления факта.
- Новое устройство из каталога должно быть представлено в первой реплике клиента;
  известное модели устройство можно обработать и позже. Это ограничивает
  случайные упоминания оборудования в советах оператора.
- Уже существующее текущее состояние того же объекта сохраняется.
  Источник — точная цитата и координаты в исходной реплике.
- По умолчанию начало нового текущего состояния — время звонка; явная однозначная
  прошедшая дата учитывается отдельно. Неизвестное историческое начало не угадывается.

Новые правила подключены через существующий `fact_recovery` и нормализатор:
их получает обычный путь обработки ответов, а не только экспериментальный скрипт.
Флаг `FACT_RECOVERY=1` должен оставаться включённым. Идентификатор политики
в метаданных — `explicit-current-per-object-v2`.
Счётчики отдельно учитывают добавленные факты и изменения существующих.
Обработка не меняет входные структуры и повторно не добавляет те же факты.

  Это не доказательство проверки этой зависимости на сервере с новым коммитом.

- `git diff --check`: успешно.

- Оба официальных оценщика сохранены без изменений. Хеши входят в VERIFICATION.json.

- Отдельная диагностическая выборка из 80 train-аккаунтов (94 звонка): только
  модуль восстановления услуг без ответов модели дал 16 фактов, 7 совпавших

- Ошибки остались. Увеличение полноты оплачено небольшим снижением P и G.
  Правила намеренно воздерживаются от неоднозначных объектов и конфликтов.

## Как воспроизвести

Из корня репозитория в рабочем окружении проекта. Пути ниже нужно заменить своими;
каталог результата должен быть новым. Передавать нужно именно `raw-answers.jsonl`,
а не только уже нормализованные предсказания.

```bash
python -m unittest discover -s tests
python -m compileall -q src tests docs/experiments/current-state-recovery-001
python docs/experiments/current-state-recovery-001/replay.py \
  --gold /path/to/organizer-v2.1/val.jsonl \
  --catalog /path/to/organizer-v2.1/catalog.json \
  --raw /path/to/4090-003-datefix-full-001/raw-answers.jsonl \
  --reference-pred /path/to/4090-003-datefix-full-001/predictions.jsonl \
  --output-dir out/current-state-recovery-replay-new
```

Скрипт сохраняет сравнение, предсказания, журнал решений и изменения отдельных
состояний. Персональные данные и эти подробные результаты не публикуются в GitHub.
`base_fact_recovery.py` — замороженная собственная реализация из `6f511af`,
нужная для честного контроля на тех же сырых ответах.

## Что делать команде

1. Получить эту ветку и сравнить изменения с собственной веткой памяти.
   Автоматически в main здесь ничего не слито.
2. Использовать новые итоговые предсказания из переданного архива результатов:
   `reproduced-final/after.jsonl`. Сырые ответы и старые предсказания сохранять.
3. При объединении не потерять два новых модуля, их вызовы в `fact_recovery`,
   метаданные политики и тесты. Повторить сравнение после объединения.
4. Дополнительно проверить полный обычный путь инференса на сервере, если он
   доступен. Для данного исправления новое обучение и аренда GPU не требуются.
5. Следующий отдельный приоритет — ошибки реплики-источника и ложные добавления,
   затем пропуски с неоднозначным объектом. Проверять P/R/G вместе с T/S;
   не расширять правила только ради повышения текущего состояния.

Точные агрегаты, контрольные хеши входов и исходников — в `VERIFICATION.json`.
