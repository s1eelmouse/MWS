# Отложенная проверка targeted 005, batch=4

Подготовлен отдельный сценарий. Он не меняет установленный пакет обучения,
его manifest, train.py, данные или родительские веса. На момент подготовки
серверные команды агентом не выполнялись.

Основание для попытки batch=4: на 4090 при batch=2 измерены CUDA allocated
около 4.58 GiB, reserved около 5.85–6.22 GiB, всего VRAM около 24 GiB.
Запас позволяет ожидать работоспособность batch=4, но пиковую память нельзя
гарантированно получить простым умножением. Padding, длинные входы и KV-cache
зависят от состава batch и длины сгенерированных ответов.

## Порядок

1. Пользователь загружает новый standalone script, без переустановки обучения.
2. Пользователь ставит ОДИН набор, Noisy или Clean, в tmux-очередь.
3. Пока `005-targeted-001/pipeline-status.json` не подтверждает завершение и
   наличие merged-весов, процесс только читает статус раз в 30 секунд. GPU
   не используется. Ошибка обучения останавливает ожидание; тайм-аут 150 минут.
4. После завершения берётся общий pipeline-lock, проверяются модель/данные/код
   и минимум 16 GiB свободной памяти.
5. По числу токенов prompt выбираются восемь самых длинных звонков выбранного
   набора. Два batch по четыре, плюс warmup, проверяются штатным benchmark.
   Эта переставленная выборка помечена diagnostic_subset и не включается
   в общую ресурсно-качественную кривую/оценку полного качества.
6. При ошибках probe или резерве больше 90% VRAM полный val не запускается.
   Если probe проходит, запускается ровно ОДИН полный val из 383 звонков,
   в исходном порядке, batch=4. Автоматического уменьшения batch в измерениях нет.

Сохраняются все прежние метрики benchmark: official 2.1, diagnostic/per_attribute/
grounding_diagnostics, raw и обработанные ответы, failed с накоплением,
calls/batches/memory.csv, allocated/reserved/RSS, токены, p50/p95, throughput,
GPU-секунды и окружение. Настройки грамматики, дат, recovery и памяти прежние.

Успешный probe не является доказательством, что любой полный batch никогда
не исчерпает память: ответы остальных звонков могут оказаться длиннее.
При полном benchmark OOM останется явной ошибкой, не скрытым переходом на batch=2.
Возможны различия генераций из-за численной арифметики при другом batch.

## Запуск

На ноутбуке, обычный PowerShell:

```powershell
powershell -ep Bypass -File "$HOME\Desktop\MWS\outputs\Val4.ps1" Upload
```

Можно поставить в очередь уже во время обучения; будет проверен только noisy:

```powershell
powershell -ep Bypass -File "$HOME\Desktop\MWS\outputs\Val4.ps1" Noisy
```

Для исходного val вместо Noisy указать Clean — это отдельный запуск, не
автоматическое добавление второго полного val. Сразу два набора не требуются.

На сервере смотреть шумную проверку:

```bash
tail -n 40 -f ~/mws-v21/out/005-targeted-001-val-noisy-b4-001.log
```

Сначала будет WAITING FOR TRAINING, затем memory-probe, затем полные
`Completed .../383; failed: ...`. Ctrl+C останавливает только просмотр.

Результаты: `~/mws-v21/out/005-targeted-001-val-noisy-b4-001/validation/report.json`.
Для Clean используется `...-val-clean-b4-001/`. Probe и его логи хранятся
отдельно в папке того же запуска. Повторная запись поверх результатов запрещена.

## Сопоставимость ресурсов

Для сравнения batch=1 и batch=4 нужны **одни и те же веса, входные звонки и
профиль**. Старый batch=1 другой модели не является парным замером этой.
Полный batch=4 даст одну корректную точку нового кандидата. Ресурсные точки
на одинаковом меньшем фиксированном срезе можно измерить отдельно позже,
не обязательно двумя полными val. Качество малого среза не заменяет полный val.
Скорость новой модели batch=4 против родителя batch=2 не изолирует эффект весов.

Локально проверены ожидание завершения, отказ после ошибки обучения, выбор
действительно длиннейших prompt без передачи gold в prompt builder и
неизменность входных записей: три теста прошли. GPU probe выполнит пользовательский
сервер после завершения обучения.
