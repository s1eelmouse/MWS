## 4. Решение 1: JSON по построению

XGrammar компилирует `Facts.model_json_schema()` в грамматику. На каждом шаге
разрешены только токены, продолжающие корректный JSON.

| Было | Стало |
|---|---|
| 22 отказа | **0 отказов** |
| 94 % формата | **100 %** |
| recall 0,3675 | **0,3908** |
| state 0,3339 | **0,3467** |

Recall/state — пакет 1; сам эффект формата (22→0, 94→100 %) переносится на 2.1.

> Notes: ограничение не меняет prompt и подпись адаптера. Это не постобработка,
> а гарантия синтаксиса/типов/enum.

## 6. Решение 3: даты считает код, а не модель

`TEMPORAL_NORMALIZATION=task`:

- `ticket_status`: «сегодня», «вчера», «N дней назад», «с пятницы»;
- `action`: явное время, иначе `started_at`;
- `agreement`: явное будущее время = дата события;
- «принята» переносится внутри одной серии `account_id`;
- типичные ASR-искажения cue («вчира», «чирез»).

| Модель | Без дат | С `task` (batch / HTTP) |
|---|---:|---:|
| continue-002 | 0,3566 | 0,4237 / 0,4000 |
| continue-003 | — (не мерили) | **0,4377 / 0,4351** |

Это пакет 1, историческая динамика. На 2.1 те же предсказания 003 дают T 0,4492;
код дат тот же, изменилась метрика. Главный разрыв 2.1 — не даты, а state/tariff.

> Notes: модель по-прежнему пишет ISO-даты; код проверяет и пересчитывает их от
> `started_at`. Это не меняет prompt, схему и адаптер.

## 9. Что проверили и отклонили

| Гипотеза | Результат |
|---|---|
| Глобальный repetition penalty | ломает качество/грамматику |
| Фильтр длинных `agreement` | precision растёт, temporal падает |
| Массовое закрытие `valid_to` | T −0,0059, S −0,0032 |
| Починка source по словам | нестабильно на половинах val |
| 1.7B | вне лимита 1,5B, нужен ментор |
| Синтетика учителем | запрещена в локальной валидации, не чинит даты |

> Notes: это сильный слайд для «глубины проработки»: мы не только добавляли, но и
> измеряли и откатывали.
