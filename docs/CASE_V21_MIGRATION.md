# Переход на данные и оценщик организаторов 2.1

Это описание текущего кода, подготовленного 14.11.2026. Старые отчёты, веса,
адаптеры и снимки кода сохранены. Их метрики относятся к старому оценщику и
не подменяются новыми числами.

Дополнено после объединения идей ветки `codex/organizer-v21-state-accuracy`:
[состав, проверка и результаты](TEAM_V21_INTEGRATION.md). Новый комплект для V100 —
`case-v21-002`. Предыдущий `case-v21-001` не включает эти дополнения.

## Что изменено

- По умолчанию используется `data/organizer-v2.1`, отдельно от прежнего
  `data/organizer`. Новые исходные файлы скопированы побайтно; разбиение
  организаторов сохранено: 3926 train, 383 val, пересечения клиентов нет.
- Схема, сериализация обучающих ответов и XGrammar теперь допускают пустое
  `object.name`, встречающееся в новой разметке. Поля, enum, даты, интервалы и
  источники продолжают проверяться. Тип `other` оставлен: он есть в новых данных.
- XGrammar строится из той же схемы `Facts`, что применяется при валидации.
  Отдельного расходящегося JSON-шаблона нет. Проверка настоящей компиляции и
  приёма ответа с пустым именем выполняется при наличии ML-зависимостей.
- `train`, `prepare_case`, `check_data`, `predict`, `benchmark`, `eval`,
  `compare_temporal`, `compare_runs`, `run_experiment`, HTTP и журналы учитывают
  новую версию. Docker-конфигурация обучения рассчитана на CUDA 12.6.
- Оба официальных оценщика сохранены без изменений с закреплёнными SHA256:
  `official_case_metrics.py` — старый, `official_case_metrics_v21.py` — 2.1.
  Обёртка создаёт отдельный экземпляр оценщика и каталога для каждого сравнения.
- Диагностика дат теперь отдельно показывает ошибки всех сопоставленных фактов
  и ошибки фактов, реально входящих в знаменатель нового `temporal_recall`.
  `action` в эту метрику 2.1 не входит; `agreement` входит при выполнении условий
  официального оценщика. По каждому атрибуту сохраняются и показатели состояний.
- Сравнение ресурсных точек запрещает смешивать разные версии оценщика, каталог,
  локальную поправку, датасет, ограничения и настройки обработки.

## Как теперь читать качество

Опубликованная база 2.1 воспроизведена **точно** на всех 383 звонках:

| Метрика | База 2.1 | Цель при допуске −0,02 |
|---|---:|---:|
| fact_precision | 0.3348 | — |
| fact_recall | 0.3805 | — |
| temporal_recall | 0.4706 | 0.4506 |
| state_accuracy | 0.5345 | 0.5145 |
| grounding_turn | 0.7835 | — |

Отсечение по времени при допуске −0,05: 0.4206. Это арифметика по опубликованной
базе и формулировке кейса; окончательное применение правил остаётся за жюри.

Контрольный пересчёт старых сохранённых ответов второй модели с объединённой
историей дал temporal_recall **0.4081**, state_accuracy **0.4270**. Это **не новый
прогон**: в новом val изменились входы 24 звонков. Эти числа показывают, почему
нужна новая полная генерация, и не свидетельствуют о выполнении порогов.
Адаптация формата сама по себе не улучшает качество весов.

## Совместимость со второй моделью

Изменение допустимого имени меняет подпись контракта. Не надо переписывать
`case_contract.json` старой модели или выдавать её за заново обученную.

Для известной старой подписи предусмотрен явный переход:

- инференс: `ALLOW_LEGACY_CONTRACT=1`;
- новый цикл обучения из старого адаптера:
  `--init-adapter-dir /path/to/adapter --allow-legacy-contract`;
- объединение непосредственно старого адаптера:
  `merge.py --allow-legacy-contract ...`.

Неизвестные подписи по-прежнему отклоняются. В отчёт попадают исходная и целевая
подписи, правило совместимости и факт отсутствия изменения весов. Готовый новый
адаптер или результат merge получает текущий контракт с указанием происхождения.
`--with-schema` не служит обходом проверки локальных весов.

Для возобновления прерванного старого обучения используйте его исторический
снимок кода и данные. Новый train/val — **новый цикл с новым output-dir**, а не
незаметная замена датасета в прежнем checkpoint.

## Режимы оценщика и известная ошибка организаторов

`SCORER_VERSION=2.1` — основной официальный режим. `eval` и `compare_temporal`
также принимают `--scorer-version`. Для исторического сравнения есть режим `1`;
указывайте прежние gold и каталог явно.

В официальном `recover_dates` найдены два вызова `set.update` с отдельными датами
вместо списка: определённые фразы про две недели и позапрошлый период вызывают
`TypeError`. На новом val эти ветки не срабатывают; опубликованная база считается
без поправок. На произвольных данных код может остановиться с явной ошибкой.

Для диагностики есть отдельный `2.1-datefix`: исправлены только два аргумента
`update` в изолированной функции, исходный официальный файл не меняется.
Отчёт фиксирует название поправки и хеш адаптера. Это **локальный вариант**, его
нельзя молча выдавать за официальный или смешивать с ним в графике. На новом val
результат базы с поправкой и без неё совпал полностью. Подготовленный серверный
запуск использует официальный `2.1`.

## Логи и воспроизводимость

Общий `run_context` содержит версии и подписи схемы, JSON-грамматики, оценщика,
каталога и SHA256 исходных train/val. Он записывается в обучение, попытки,
инференс и оценку. Контрольные суммы относятся к фактическим байтам файлов.

При обучении сохраняются параметры, seed, происхождение адаптера, окружение и
пакеты, точность FP16/BF16, Trainer checkpoints и состояние оптимизатора,
loss/eval_loss, шаг/эпоха/LR/grad_norm, длительность, RSS процесса и текущая/пиковая
выделенная и зарезервированная память CUDA. Журнал событий не зависит от удаления
старых checkpoints. Для V100 выбирается FP16, а не эмулируемый BF16.

**eval_loss не является качеством сгенерированных фактов.** Официальные
precision/recall, время, состояния и grounding появляются после отдельной
генерации и сравнения с gold. Валидация не используется для обновления весов.

При полной проверке сохраняются:

- `report.json`, `metrics.json`, `environment.json`: качество, окружение,
  точность, подписи, время загрузки, компиляция грамматики, настройки истории;
- `predictions.jsonl`, `predictions-before-series.jsonl`: итоговые ответы и
  ответы до истории для проверяемого сравнения;
- `calls.jsonl`, `batches.jsonl`, `failures.jsonl`, `raw-answers.jsonl`:
  длительности, токены, причины ошибок, повторные генерации, исходные ответы;
- `memory.csv`: выборки RSS процесса; в отчёте RSS и пики аллокатора CUDA,
  latency p50/p95, пропускная способность, GPU-секунды на 1000 звонков;
- `errors.jsonl`, `temporal-audit.jsonl` (если были решения по датам),
  `history-date-comparison/`: ошибки фактов, решения календаря и вклад истории;
- `preflight/`: проверки данных, полный журнал тестов, SHA256 релиза, проверка
  исходных весов, настройки и статус всей цепочки;
- `quality-vs-baseline.json`: база 2.1, новые показатели и разница с базой.

GPU-секунды здесь — длительность локальной обработки × одна используемая GPU,
не сумма времени отдельных CUDA-ядер. На общем сервере чужая нагрузка может
увеличивать задержки. Ограничение памяти не резервирует GPU; сравнение V100 и
старых 4090-измерений не доказывает ускорение архитектуры на одинаковом железе.

## Запуск на новом сервере без обучения

Сценарии лежат в `docs/evaluations/continue-002-v21`. Для текущей передачи
подготовлены их копии и проверенный архив в локальной папке `MWS/outputs`.
Сначала выполните **на своём ПК в PowerShell**:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Users\Tripozik\Desktop\MWS\outputs\Deploy-CaseV21.ps1" -Stage Upload
```

Будут переданы только код и новый пакет данных; весов и нового окружения в архиве
нет. Установка идёт в `~/team_shpana/releases/case-v21-002`. Архив и каждый файл
проверяются по SHA256. Уже установленная идентичная версия повторно не меняется;
замена другой версии под тем же именем отклоняется. Прежние файлы сохраняются.
Доступ нужен из сети университета; пароль ключа вводится обычным способом.

Посмотрите `nvtop` на сервере. По умолчанию процесс имеет бюджет CUDA-аллокатора
12 GiB; перед запуском требуется хотя бы 14 GiB свободной VRAM. Это начальная
настройка для общей V100, а не уже измеренный максимум. Затем **на ПК**:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Users\Tripozik\Desktop\MWS\outputs\Deploy-CaseV21.ps1" -Stage Run
```

Сценарий запускает `tmux`, использует готовую `.venv-v100` и
`models/continue-002`; проверяет хеш именно второй модели. Сначала выполняет
тесты, проверку всех данных и воспроизведение базы, затем генерирует ответы на
все **383 звонка нового val**, batch=1, XGrammar `torch_native`, `case_v2`,
восстановление текущих фактов с защитами, объединённая ограниченная история
и точный каталог. Gold не передаётся модели.
Фраза `Completed N/383; failed: K` выводится после каждого пакета. Переподключение
SSH и сон ноутбука не прерывают процесс.

Для просмотра **в SSH-сеансе**:

```bash
tail -n 40 -F ~/team_shpana/out/continue-002-v21-full-val-002.log
```

`Ctrl+C` завершает только просмотр журнала. Финал — `DONE: .../report.json` и
`preflight/pipeline-status.json` со статусом `complete`. Отказы отдельных звонков
видны отдельно; `complete` означает завершение измерения, а не нулевое число ошибок.

При нехватке памяти или другой ошибке сохраните журнал. Повторный запуск требует
нового имени: например, добавьте `-RunId continue-002-v21-full-val-003`.
Бюджет памяти можно изменить `-BudgetGiB 16`, согласовав свободную VRAM с командами.
Один полный запуск — одна точка ресурсов; три точки и шумовой срез остаются
отдельной работой после анализа качества этой проверки.

## Будущее обучение на новой разметке

Сейчас обучение **не запускается**. При необходимости новый цикл можно начать
из второй версии адаптера. Из каталога нового релиза с активной `.venv-v100`:

```bash
export BASE_MODEL=Qwen/Qwen3-0.6B
export CASE_DATA_DIR="$HOME/team_shpana/releases/case-v21-002/data/organizer-v2.1"
export CATALOG_PATH="$CASE_DATA_DIR/catalog.json"
export SCORER_VERSION=2.1
python src/train.py --check-data
python -u src/train.py --init-adapter-dir "$HOME/team_shpana/adapters/continue-002" \
  --allow-legacy-contract --epochs 1 --batch-size 1 --learning-rate 0.0001 \
  --save-steps 50 --output-dir "$HOME/team_shpana/out/continue-v21-train-001"
```

Это новый optimizer и новый цикл, не точное продолжение старого scheduler.
Ещё одна эпоха не гарантирует роста качества; решение принимается по новой
полной проверке. При ограниченной памяти первым делом нужен короткий smoke.
