# Отчёт по тренировкам: что обучали и что получилось

- **Дата:** 14.11.2026
- **Модель:** `Qwen/Qwen3-0.6B`, 596 049 920 параметров
- **Метод:** QLoRA, 4-bit NF4 + double quantization, LoRA r=16, α=32, dropout 0.05, all-linear
- **Данные:** train — 3 926 звонков / 18 475 фактов; val — 383 звонка / 1 845 фактов. Gold не попадал в prompt.

Этот отчёт отвечает на три вопроса
- **что именно обучали**
- **что из этого следует**
- **чему ещё нет доказательств**

Числа взяты из отчётов и сохранённых артефактов; прочерк «—» значит «не зафиксировано», а не ноль.

## Если у тебя две минуты

1. Мы сделали три последовательных цикла обучения 0.6B: `001` → `002` → `003`. Это три полных прогона на 4090; ещё один технический smoke был на 4060 и нужен только для проверки железа.
2. Constrained JSON убрал 22 отказа из 383 и дал 100 % валидного формата. Главный прирост T дал не ещё один проход по train, а детерминированная обработка дат: на `002` она добавила **+0.0671 T**.
3. На пакете 2.1 `003` без recovery даёт **T 0.4492 / S 0.4350**; с recovery — **T 0.4663 / S 0.5152**. Это пересчёт сохранённых предсказаний, а не свежий end-to-end прогон. Первая половина val слабее: **T 0.4096 / S 0.4907**.

## Словарь

| Обозначение | Полное название | Что именно считает |
|---|---|---|
| **T** | `temporal_recall` | Среди сопоставленных фактов с датой, которую можно восстановить из транскрипта, — доля фактов с правильными `valid_from`/`valid_to`. Это не «доля всех фактов». |
| **S** | `state_accuracy` | Среди текущих состояний по однозначным атрибутам (последний факт по паре объект-атрибут) — доля с правильным значением. |
| **P** | `fact_precision` | Доля предсказанных фактов, которые сопоставились с эталоном. |
| **R** | `fact_recall` | Доля эталонных фактов, которые нашлись в предсказании. |
| **G** | `grounding_turn` | Доля сопоставленных фактов, у которых правильно указана реплика-источник. |
| **формат** | `format_valid_rate` | Доля звонков с валидным JSON по схеме. |
| **отказы** | `failed_calls` | Звонки, где ответ не распарсился или не прошёл проверку. |

Дополнительные термины:

- **`task`** — пофактные правила дат: «вчера», «N дней назад», «с пятницы», «через неделю».
- **серии** — перенос дат между звонками одной истории (например, «принята» → «в работе»).
- **recovery** — детерминированное добавление текущего тарифа/статуса, **только если** модель не предсказала текущее состояние. Не перезаписывает модель.

## Два пакета — две разные таблицы

Нельзя сравнивать абсолютные числа пакета 1 и пакета 2.1: в 2.1 изменились разметка, часть входных полей, оценщик и появился каталог. Поэтому ниже **две отдельные таблицы**.

- **Пакет 1** — старые данные и старый оценщик. На нём обучены `001`, `002`, `003`.
- **Пакет 2.1** — новый пакет. `003` на нём только **пересчитан** по сохранённым предсказаниям; модель обучена на старом train.

## Что меняли и в каком порядке

Это не чистый A/B «одна эпоха против трёх»: между шагами менялись сразу три вещи — число эпох, constrained decoding и обработка дат. Поэтому ниже показаны **отдельные сравнения**, где меняется только один фактор.

| Шаг | Что включили | Зачем | Результат (пакет 1) |
|---|---|---|---|
| 1 | `001`, одна эпоха | Базовая точка | Свободная генерация: T 0.3348 / S 0.3339, 22 отказа, формат 94.3 % |
| 2 | XGrammar | Убрать битый JSON | **22 → 0 отказов, 94.3 → 100 % формата**; recall 0.3675 → 0.3908, state 0.3339 → 0.3467 |
| 3 | `002`, +1 эпоха | Больше обучающих проходов | Constrained без дат: T 0.3315 → **0.3566** (+0.0251), S 0.3467 → **0.3852** (+0.0385) |
| 4 | `task` + серии | Даты кодом | T 0.3566 → **0.4237** (+0.0671), S и P/R не меняются |
| 5 | `003`, +1 эпоха | Ещё один проход | T 0.4237 → **0.4377** (+0.0140), S 0.3852 → **0.3949** (+0.0097) |

**Как это читать:**

1. *Честное сравнение одной модели*: меняется только декодирование. T даже чуть просел (−0.0033), зато исчезли отказы и выросли recall/state.
2. *Честное сравнение эпох*: `001` и `002` обе constrained и без дат.
3. *Честное сравнение постобработки*: та же `002`, меняются только даты. Это **самый большой прирост T**.
4. *Честное сравнение эпох*: `002` и `003` обе с датами. Третья эпоха добавила уже немного.

Чего в таблице **нет**: отдельного числа `003` без дат. Поэтому мы не утверждаем, что «каждая эпоха улучшала всё» при любом режиме. Мы сравниваем `001`→`002` без дат и `002`→`003` с датами — это два разных, но честных сравнения.

¹ У базы 34 ответа не проходят строгую проверку схемы обвязки, но их читаемые факты официальный оценщик учитывает; это не 34 пустых ответа.

² Строка `002` в свободной генерации — статистический артефакт: 347 из 383 ответов отклонены, T и S посчитаны на 72 совпавших фактах. Её нельзя сравнивать с остальными; она показывает только масштаб проблемы формата.

Для `002` и `003` T указан с переносом дат внутри серий. Без серий, в HTTP-режиме: `002` — 0.4000, `003` — 0.4351. Precision, recall, state и grounding от режима серий не меняются.

## Качество на пакете 2.1

383 звонка, официальный оценщик v2.1. Цели: **T ≥ 0.4506**, **S ≥ 0.5145**; отсечение — **T < 0.4206**.

| Модель / режим | T | S | P | R | G | Формат | Статус |
|---|---:|---:|---:|---:|---:|---:|---|
| База glm-5.3 (2.1) | 0.4706 | 0.5345 | 0.3348 | 0.3805 | 0.7835 | — | Официальная база |
| `003`, сохранённые предсказания | 0.4492 | 0.4350 | 0.5003 | 0.4986 | 0.7141 | 100 % | Диагностика: 24 val-звонка имеют изменённые входные поля |
| `003` + recovery | **0.4663** | **0.5152** | 0.4929 | 0.5279 | 0.7023 | 100 % | **Обе цели достигнуты на сохранённых предсказаниях** |
| `002`, новая генерация на V100: `case_v2` + recovery + история | 0.4709 | 0.4767 | 0.4792 | 0.5117 | 0.7150 | 100 % | Свежий полный прогон; цель по T выполнена, по S — нет |

**Что здесь важно:**

- `003` обучена на старом train, а оценена на новых gold. У 24 val-звонков изменились входные поля. Это диагностика потенциала, а не свежий замер.
- Recovery поднимает T и S, а P/R меняет умеренно: precision падает на 0.0074 (0.5003 → 0.4929), recall растёт на 0.0293 (0.4986 → 0.5279). Он добавляет только отсутствующее текущее состояние.
- Запас по S маленький: **0.5152 при цели 0.5145**, то есть 0.0007. Поэтому «обе цели достигнуты» — это про конкретный сохранённый срез, а не про гарантию на скрытом тесте.

По половинам val картина неровная:

| Половина | `003` без recovery | `003` + recovery |
|---|---:|---:|
| первая, 191 звонок | T 0.3957 / S 0.4130 | T 0.4096 / S 0.4907 |
| вторая, 192 звонка | T 0.5018 / S 0.4585 | T 0.5216 / S 0.5415 |

Recovery улучшает обе половины, но первая всё равно ниже цели по T и S. Это ограничение модели, а не правила recovery.

## Что мы можем и чего не можем утверждать

| Утверждение | Статус |
|---|---|
| Constrained JSON убирает отказы | **Подтверждено** на 383 звонках: 22 → 0, формат 94.3 → 100 % |
| Даты кодом дают основной прирост T | **Подтверждено** на `002`: +0.0671 T при неизменных S/P/R |

| Модель устойчива на скрытом срезе | **Не доказано**: первая половина val ниже цели, adversarial не проверен |

## 8. Ограничения

- **`003` не проверен на шумном val 2.1.** Чистый val — 0.4377 на пакете 1; устойчивость к ASR-шуму для третьей эпохи не измерена.
- **Пересчёт 2.1 — диагностика.** Числа 0.4492/0.4350 и 0.4663/0.5152 нельзя выдавать за свежий прогон.
- **Пакеты не сравнивать напрямую.** У 2.1 изменены разметка, входные поля и оценщик.
- **Скрытый тест и adversarial не проверялись.** Все числа — на выданном val; шумный val был только у `002` на старом пакете.
- **1.7B не обучалась.** Нужно письменное разрешение ментора и проверка лимита 1.5B.
