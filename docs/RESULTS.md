Правила:

- Пустая ячейка значит «ещё не измерено», а не «ноль».
- Прочерк «—» значит, что для этого прогона величину не мерили или она к нему не
  относится: например, p95 у прогона без `benchmark.py` или GPU-секунды у CPU.
- Качество — только на полном val (383 звонка), официальным скриптом.
  Сравнение на части val допустимо, только если база посчитана на тех же звонках.
- У каждой строки есть стенд из раздела 1. Скорость и память с разных стендов
  не сравниваются и не усредняются. Метрики качества от железа не зависят.
- Числа переносятся из файлов прогона как есть. Пересчёт руками — только там,
  где это явно сказано.
- Не улучшило ни одно число — откатываем изменение, но строку оставляем.

## 0. Откуда берутся числа

Основной путь — `src/run_experiment.py` или отдельный `src/benchmark.py`
(см. EXPERIMENTS.md). Файлы одного прогона:

| Файл | Что из него берём |
|---|---|
| `environment.json` | стенд: CPU, ОЗУ, GPU, версии, коммит |
| `benchmark/<режим>/report.json` | ресурсы инференса и качество одного режима |
| `benchmark/<режим>/metrics.json` | официальные метрики и разбивка по атрибутам |
| `benchmark/<режим>/errors.jsonl` | по звонку: сколько фактов в эталоне, сколько найдено, сколько совпало, проблемы источников |
| `comparison/comparison.csv` | сводка режимов и отклонение от базы на том же срезе |
| `comparison/per_attribute.csv` | метрики пяти типов фактов для базы и каждого режима: пропуски, лишние, ошибки дат и источников, отклонения precision/recall |
| `out/val-noisy-*.jsonl`, `*.manifest.json` | зашумлённая копия val для проверки устойчивости (раздел 5) |
| `comparison/resources-quality.svg` | график для отчёта и презентации |
| `adapter/attempt-*/status.json`, `events.jsonl` | время, память и loss обучения |

Текущий `train.py` сохраняет `attempt-*` и при прямом запуске. Старые версии
до появления журнала оставляли только `training_stats_step_*.json`
(время и пик видеопамяти). Прямое предсказание через `predict.py` не мерит
задержку по звонкам. Такие строки помечаются «без benchmark», а ресурсы для них
снимаются отдельно: `benchmark.py --model <merged-модель>`.

## 2. Ресурсы инференса

### Что записываем и откуда

Определения — EXPERIMENTS.md, раздел «Единая методика». Самое важное из них:

- задержка — время всей пачки от подачи до готовых ответов; при batch > 1 у всех
  звонков пачки одно время, оно **не делится** на batch. Для сравнения стоимости
  разных batch есть отдельная колонка «секунд на звонок»;
- прогрев и загрузка модели в скорость не входят;
- GPU-секунды — время занятой карты, а не время CUDA-ядер; для CPU пусто, а не ноль;
- память — пик процесса после прогрева, включая уже загруженную модель.

| Колонка | Поле `report.json` |
|---|---|
| Режим | `settings.device`, `dtype`, `settings.batch_size` |
| Параметры | `model_parameters` |
| Размер весов на диске, байт | `model_weights_bytes`: сумма `.safetensors` и `.bin` в `model_artifacts`, без конфигурации; для удалённой модели может быть неизвестен |
| Вход p50 / p95, токенов | `input_tokens.p50` / `.p95` |
| Ответ p50 / p95, токенов | `output_tokens.p50` / `.p95` |
| Задержка p50 / p95, с | `call_completion_seconds.p50` / `.p95` |
| Секунд на звонок | `measurement_seconds / calls` |
| Звонков в час: всего / успешных | `calls_per_hour` / `successful_calls_per_hour` |
| Ошибок | `failed_calls` из `calls` |
| Пик видеопамяти | `memory.cuda_peak_reserved_bytes` (allocated — `memory.cuda_peak_allocated_bytes`) |
| Пик ОЗУ процесса | `memory.process_rss_sampled_peak_bytes` |
| GPU-с / 1000 звонков | `gpu_seconds_per_1000_calls` |
| Загрузка модели, с | `model_load_seconds` |

Все перечисленные числовые поля экспортируются в `comparison.csv`: параметры,
размер весов, время загрузки, p50/p95 токенов и задержки, скорость и память.
Имена полей сохраняются, кроме `p50_seconds` / `p95_seconds`,
`seconds_per_call` и `rss_peak_bytes`. Недоступные поля старых отчётов пустые.

### Как заполнить строки 4090-baseline-001

Качество на полном val уже есть (разделы 3 и 5). Ресурсы constrained-режима
batch2 сняты benchmark-прогоном (раздел 2). Для трёх точек кривой ещё нужны
cuda-batch1, cuda-batch4 и CPU по единой методике. Модель обучена напрямую через
`train.py`, поэтому обучение не повторяем, а меряем готовую merged-модель.
`MAX_INPUT_TOKENS` — тот же, что при обучении, иначе два длинных звонка val уйдут
в `input_too_long`.

    export MAX_INPUT_TOKENS=12288
    python src/merge.py --adapter-dir out/4090-baseline-001 --output out/merged-4090-baseline-001
    python src/run_experiment.py --output-dir out/measurements-4090-baseline-001 --model out/merged-4090-baseline-001

Merge не нужен, если `out/merged-4090-baseline-001` на сервере сохранилась.
Результат: `benchmark/{cuda-batch1,cuda-batch4,cpu-batch1}/report.json`,
`comparison/comparison.csv` и `per_attribute.csv`. Первый же прогон пишет
`environment.json` — из него заполняются CPU и ОЗУ стенда `4090` в разделе 1.
Заодно новый оценщик посчитает ошибки дат и источников по типам фактов, которых в
отчёте прогона нет (раздел 5).

Если обучение нужно повторить через `run_experiment.py`, число эпох указывается
явно: `--epochs 1`. По умолчанию там 3, а `--save-steps 50` и `--batch-size 1`
заданы в скрипте жёстко — для этого прогона они совпадают с исходными.

Источник метрик качества: `quality.official` в `report.json` (или `official`

Отклонение от базы на том же срезе — колонки `*_delta_from_baseline`
в `comparison.csv`.
Отклонения считаются для всех пяти официальных метрик и `format_valid_rate`:
значение модели минус значение базы, в долях единицы. Неопределённая метрика
остаётся пустой и в отклонении.

Метрики базы — пересчёт приложенным скриптом; числа из отчёта организаторов и пороги
см. README, раздел 1: цель `temporal_recall` ≥ 0.401, `state_accuracy` ≥ 0.328,
отсечение `temporal_recall` < 0.371. Время работы базы из её предсказаний
восстановить нельзя, поэтому её ресурсы — «?» до ответа организаторов.
На графике база — пунктирная линия качества, а не точка.

**Подтверждённая контрольная — `4090-continue-002` с constrained JSON и датами
`task`.** Сырая вторая эпоха уже лучше baseline по всем метрикам: `temporal_recall`
0.3315 → 0.3566, `state_accuracy` 0.3467 → 0.3852, precision / recall
0.3625 / 0.3908 → 0.4008 / 0.4119, grounding 0.7656 → 0.7987. `benchmark.py`
поднимает `temporal_recall` до **0.4237** с сериями; без переноса (HTTP) — 0.4000.
Модель подтверждена на чистом и шумном val.

**Текущий кандидат — `4090-continue-003` + recovery v2.** На свежем полном val
2.1: **T 0.4807, S 0.5201**, P/R 0.4965 / 0.5328, G 0.7121, 0 отказов, 100 %
формата. На чистом val обе цели 2.1 пройдены; первая половина по S (0.5031)
ниже цели. На шумном val 2.1 — T 0.4582 / S 0.4141: T проходит цель, S нет.
Поэтому `continue-002` остаётся production/fallback, а следующий шаг — 004 или
005 на `train_variant=noise`. Старые числа 003 по пакету 1 (T 0.4377 с сериями)
остаются историей и с 2.1 не смешиваются.

**4090-baseline-001 и его constrained-версия без дат `task` отсечение не проходят:**
`temporal_recall` 0.3348 и 0.3315 ниже порога 0.371. Ограничение убрало 22 отказа
(100 % валидного формата), подняло recall 0.3675 → 0.3908 и `state_accuracy`
0.3339 → 0.3467, precision после dedup 0.3625, grounding 0.7656. Старая версия по
остальному тоже лучше базы: precision +0.128, recall +0.119, grounding +0.085.
У старой версии совпало 678 фактов, верные даты у 227; у constrained — 721.
Подробно — разделы 14–17 [отчёта](experiments/4090-baseline-001/REPORT.md).

Разбор 678 совпавших фактов: у 227 обе даты верны, у 262 неверен только
`valid_from`, у 15 только `valid_to`, у 174 обе. Главная потеря — начало
интервала, а не конец. Хуже всего `ticket_status` (100 только `valid_from` и
96 обе) и `service_state` (62 только `valid_from`). Из 436 неверных начал
106 отличаются от эталона на ±1 день (72 — на −1): модель часто ошибается
именно в календарной поправке относительного выражения. Это подтверждает, что
даты нужно считать кодом от `started_at`, а не просить модель угадывать
абсолютные значения. По реплике-источнику ошибки начала распределены так:
`relative_day` 90 из 166, `weekday` 68 из 92, `week/offset` 129 из 159,
`no_cue` 176 из 300. Нормализатор должен покрывать «вчера/сегодня/завтра»,
дни недели и «через/назад N»; для `no_cue` дата часто не выводится из текста.

### Второй цикл 4090-continue-002

Второй QLoRA-цикл (старт с `4090-baseline-001`, LR 1e-4, +1 эпоха) снизил
`eval_loss` 0.1529 → 0.13454. Свободная генерация действительно непригодна:
347 отказов из 383 (344 `invalid_json`, 3 `invalid_schema`) и recall 0.039 из-за

## 5. Разбор ошибок по типам фактов

Атрибуты, которые меняются во времени, отдельно от статических — этого прямо требует
критерий «Глубина проработки». Прогон: 4090-baseline-001, полный val.

Все колонки считаются автоматически: поле `per_attribute` в `metrics.json` (и в выводе
`eval.py --json`), для базы и каждого режима — `comparison/per_attribute.csv` с
отклонениями precision/recall от базы. Поле `attribute_kind` разделяет временные и
статические атрибуты.

| Колонка | Поле `per_attribute.<атрибут>` |
|---|---|
| Эталон / Найдено | `n_gold_facts` / `n_pred_facts` |
| Precision / Recall | `fact_precision` / `fact_recall` |
| Совпало | `matched_facts` |
| Пропуски / Лишние | `missed_facts` / `extra_facts` |
| Ошибка даты | `date_errors`: неверное начало или конец; отдельно `valid_from_errors`, `valid_to_errors` |
| Ошибка источника | `source_turn_errors`: неверная реплика `turn_idx` |
| temporal_recall / grounding по типу | `temporal_recall` / `grounding_turn` |

Вывод: объект и полярность — не главная потеря; главная — формулировки значений

заметного эффекта, а расширение recall качества извлечения — дало бы.

Прогон оценивался до появления счётчиков типов ошибок, поэтому эталон, найдено,
precision и recall — из его `per_attribute`, совпавшие (precision × найдено, в сумме

официальных долей (678 × (1 − 0.3348) и 678 × (1 − 0.7758)). Ошибки дат и источников
по отдельным типам — прочерк до замера новым оценщиком (раздел 2). Главный источник
лишних фактов — `agreement`: 902 несовпавших записи, около 71 % всех лишних.

ошибок дат 32; `tariff` — 70 из 146, 53; `ticket_status` — 319 из 400, 165; `action` —
14 из 368, 7; `agreement` — 17 из 478, 9. Обе модели хуже всего справляются с
состояниями услуги, действиями и договорённостями.

### Сбои генерации

Из `report.json`: `error_counts` содержит количество звонков с каждой явной ошибкой,
включая нули для стандартных типов и любые дополнительные типы. В `comparison.csv`
есть колонки `errors_invalid_json`, `errors_invalid_source` и остальные `errors_*`,
а также JSON-колонка `error_counts` без потери дополнительных типов.

и дат не считаются сбоями генерации. У старых отчётов без счётчиков поля пустые;
для ручного разбора доступны `errors.jsonl` (поле `error`) и `failed_calls`.
Цель — ноль: корректная схема на

### Устойчивость к шуму

Замена скрытому adversarial-подмножеству: копия val с усиленным ASR-шумом.
Исходный val не меняется. Копию делает `src/make_noisy_val.py`:

    python src/make_noisy_val.py --input data/organizer/val.jsonl --output out/val-noisy-015.jsonl --level 0.15 --seed 42

`--level` — доля слов, которые дополнительно портятся: путаница похожих звуков
(о/а, т/д, с/з…), выпавшие и переставленные буквы, выпавшие и склеенные слова,
оборванные реплики с « —». Копия детерминирована по seed. Меняются только тексты
реплик; факты, значения, даты и `turn_idx` прежние, а span и цитата обнуляются,
потому что больше не указывают в изменённый текст. Рядом пишется
`*.manifest.json` с хешами, параметрами и долей изменённых слов: при `--level 0.15`
на val изменено 19 % слов.

Затем на копии запускается тот же замер модели:
`benchmark.py --input out/val-noisy-015.jsonl …` или
`run_experiment.py --val out/val-noisy-015.jsonl --model …`. Сравнивать с базой на
шумной копии нельзя: её предсказания сделаны по чистому тексту.

| Вариант | Прогон | Уровень шума | temporal_recall | state_accuracy | precision / recall | Валидная схема |
|---|---|---|---|---|---|---|
| База на исходном val | baseline_pred | 0.25 | 0.4205 | 0.3194 | 0.219 / 0.249 | 91 % |
| Наша модель на исходном val | 4090-baseline-001 | 0.25 | 0.3348 | 0.3339 | 0.347 / 0.368 | 94 % |
