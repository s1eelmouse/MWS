# Даты и шум под оценщик 2.1

Дополняет [ORGANIZER_DATA_UPDATE_V2_1.md](ORGANIZER_DATA_UPDATE_V2_1.md): там — что
изменилось в пакете, здесь — что это значит для чтения дат и шумовых проверок.
Всё посчитано на CPU по пакету v2.1 без модели. Предсказаний моделей в Git нет,
поэтому **эффект правил на `continue-003/004` здесь не измерен**; команды — в разделе 5.
По записи в [RESULTS.md](RESULTS.md) сохранённые предсказания `continue-003` дают на
v2.1 T 0,4492, а с восстановлением фактов — 0,4663 при цели 0,4506; обе цифры получены
после `task`.

## 1. Что оценщик 2.1 проверяет в датах

- Только `service_state`, `tariff`, `ticket_status`, `agreement`. **`action` исключён,
  `agreement` добавлен.**
- Только совпавшие факты, у которых эталонная дата есть среди дат, восстановленных
  банком выражений оценщика из **любой** реплики звонка. На val это 899 фактов из 1 477.
- Нужны обе даты по дню: `valid_from` и `valid_to`.

Какие даты вообще выводимы (val, 899 проверяемых фактов): из текста звонка — 699
(0,778), с историей серии — 732 (0,814). Остальное недостижимо: начало закрытого
«работает нормально» и старого тарифа лежит за сотни дней до звонка (125 фактов), а
«на прошлой неделе», «месяц назад», «в прошлом месяце» в эталоне — случайный день
периода (для «месяц назад» −28…−31 поровну). Планка glm-5.3 даёт 0,4706.

## 2. Что не так с режимом `task`

Он писался под оценщик v1:

- меняет даты `action`, которые больше не оцениваются;
- не трогает `service_state` и `tariff`;
- **портит верные даты договорённостей.** Если в реплике есть «завтра/через неделю»,
  дата уходит в будущее. В эталоне так датированы только договорённости из каталога.

В эталоне два слоя разметки, и от шума они не зависят:

| Значение факта | Дата в эталоне | Проверка |
|---|---|---|
| свободная формулировка (4 временных атрибута) | дата звонка, интервал открыт | 4 133 из 4 133 в train, 393 из 393 в val |
| договорённость из каталога (13 записей) | срок в будущем | 1 248 из 1 248 в train |
| симптом из каталога | начало в прошлом, интервал открыт | 1 453 из 1 456 в train |

То же правило записано в `schema.md` v2: «дата не названа — возвращайте дату звонка».

## 3. Режим `case_v2`

`TEMPORAL_NORMALIZATION=case_v2`, код — `src/temporal_case_v2.py`. Нужен
`catalog.json` (`TEMPORAL_CATALOG_PATH`); эталон в правила не попадает.

1. Свободная формулировка → дата звонка, `valid_to=null`. Значение, лишь похожее на
   запись каталога («подтверждение по смс»), не трогается: оценщик сопоставит его с
   каталожным эталоном.
2. Договорённость из каталога → единственная будущая дата из реплики-источника или
   соседних реплик, `valid_to=null`.
3. Симптом из каталога → единственная прошедшая дата как начало; «работает
   нормально» → та же дата как `valid_to`.
4. Статус заявки → дата привязывается к ближайшему упоминанию статуса в предложении.
   «До пятницы» и «статус сменился» дают окончание, «ещё вчера была принята» — ничего.
5. Банк выражений выровнен с оценщиком: «позавчера», «пару дней назад», «дней пять
   назад», «неделю назад», «в/на <день недели>», «через неделю».

Правила писались по train; замеры — на val, официальный `evaluate()`:

| Вход | без правил | `task` | `case_v2` |
|---|---|---|---|
| Эталонные факты, даты сброшены на дату звонка — читает ли правило | 0,3281 | 0,3660 | **0,5061** |
| то же в пакетном режиме с переносом по серии | 0,3281 | 0,3660 | **0,5139** |
| Эталонные факты с эталонными датами — портит ли правило | 1,0000 | 0,9388 | **0,9878** |
| Предсказания планки glm-5.3 | 0,4706 | 0,4842 | 0,4842 |

На 700 звонках train: 0,3661 → 0,5134 и 0,9422 → 0,9925. Вторая строка снизу —
главная находка про `task`: при верных датах модели он ломает 47 договорённостей из 228.

На предсказаниях планки режимы равны: zero-shot LLM формулирует значения не так, как
эталон, и слой «свободная формулировка» срабатывает редко. Дообученная модель
повторяет формулировки эталона, поэтому её эффект лежит между строками таблицы. Он
не измерен, и по умолчанию оставлен `task`.

Закрытие цепочки статусов (`close_chains=True`) выключено: при идеальном извлечении
+0,005, на предсказаниях планки −0,018 — правило зависит от лишних и пропущенных
статусов.

## 4. Шум

Правила на зашумлённом тексте val (`make_noisy_val.py`, seed 42; доля изменённых
слов 0,19 и 0,36):

| Вход | шум | n | `task` | `case_v2` |
|---|---|---|---|---|
| Даты сброшены | +0,15 | 783 | 0,3653 | **0,5032** |
| Даты сброшены | +0,30 | 658 | 0,3602 | **0,5030** |
| Эталонные даты | +0,15 | 783 | 0,9527 | **0,9898** |
| Эталонные даты | +0,30 | 658 | 0,9453 | **0,9878** |

Два вывода для шумового прогона модели:

- **T на чистом и шумном val несравнимы.** Оценщик проверяет дату, только если её
  выражение уцелело в тексте дословно: знаменатель 899 → 783 → 658. Одни и те же
  предсказания планки дают 0,4706 / 0,4773 / 0,5094. Модель сравнивается с планкой
  на одном и том же шумном файле.
- **Оценщику нужен `catalog.json` рядом с эталоном.** Без него P/R планки
  0,3329 / 0,3783 вместо 0,3348 / 0,3805. `make_noisy_val.py` теперь копирует каталог
  к шумному файлу, а отчёт `eval.py` показывает `scorer_catalog_entries` (0 — каталог
  не найден).

Шумовой прогон самой `continue-003` не выполнен: нужны веса и GPU.

## 5. Команды для сервера

```bash
# 0. пакет в отдельный каталог; prepare_case сверяет CHECKSUMS.txt
python src/prepare_case.py --source-dir <распакованный пакет> --out-dir data/organizer_v2_1
V=data/organizer_v2_1

# 1. пересчёт сохранённых предсказаний оценщиком 2.1 (CPU, секунды)
python src/eval.py --gold $V/val.jsonl --pred <predictions.jsonl> \
  --reference-metrics $V/baseline_metrics.json --json out/v21-continue-003.json

# 2. A/B дат. Нужны даты модели ДО правил: benchmark.py применяет task к каждому звонку,
#    поэтому чистое сравнение — прогон с TEMPORAL_NORMALIZATION=off (около 49 мин на
#    RTX 4090 при 7,7 с/звонок); его predictions-before-series.jsonl — это <raw.jsonl>.
python src/postprocess_dates.py --input $V/val.jsonl --pred <raw.jsonl> \
  --output-dir out/v21-dates-task --mode task
python src/postprocess_dates.py --input $V/val.jsonl --pred <raw.jsonl> \
  --output-dir out/v21-dates-case-v2 --mode case_v2 --date-catalog $V/catalog.json
python src/eval.py --gold $V/val.jsonl --pred out/v21-dates-case-v2/predictions.jsonl
#    case_v2 поверх уже обработанного файла — оценка снизу, не A/B.

# 3. шумный val: один файл и для модели, и для планки (каталог копируется сам)
python src/make_noisy_val.py --input $V/val.jsonl --output out/noisy-v21/val.jsonl --level 0.15
python src/eval.py --gold out/noisy-v21/val.jsonl --pred $V/baseline_pred.jsonl
```

## 6. Что проверить и решить

1. **Режим дат по умолчанию** — по A/B из шага 2 на `continue-003` и на
   `continue-004-v21`. Правила не зависят от весов и применяются к сохранённым
   предсказаниям без GPU.
2. **Грамматика для старых весов.** После `c71048f` ключ `object.name` в JSON-схеме
   необязателен, значит constrained decoding для `continue-002/003` изменился. На
   20–30 звонках сверить, что формат остался 100 % и имена объектов не пропали.
3. **`grounding_turn` после переразметки.** `turn_idx` изменён у 242 из 1 845 фактов
   val и 2 418 из 18 475 train (13 %), `speaker` — у 148 / 1 555. У `continue-003`
   G 0,7141 при 0,7835 у планки; критерий кейса задан по T и S, но на слайдах G теперь
   ниже базы, пока модель не переобучена на новых источниках.
4. **Самопроверка на отложенной части train**, которую советует `README.md` пакета,
   упадёт на 5 звонках train: `recover_dates` даёт `TypeError` на «через две недели»
   и «позапрошл…». В val таких звонков нет.
