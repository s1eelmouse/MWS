## Что исправлено

Раньше `postprocess_dates.py --mode task` неявно переносил дату «принята»
между звонками, а HTTP-сервис этого не делал. Ключ учитывал имя объекта и
аккаунт, порядок определялся `call_index`. Теперь общая реализация
`src/series_history.py` подключена к офлайн-обработке, Transformers и vLLM:

1. Перенос включается отдельно: `--allow-series-history` для файла,
   `TEMPORAL_SERIES_HISTORY=1` для инференса.
2. Совпадать должны непустой `series.account_id` и идентификатор заявки:
   непустой `object.id` либо номер из имени «заявка 1234». Одного слова
   «заявка» недостаточно. Сопоставление ID с номером и нечёткое объединение
   объектов не выполняются.
3. Переносится только `valid_from` положительного `ticket_status=принята`.
   Другие статусы, факты и их порядок сохраняются.
4. Источник истории должен быть строго раньше по `started_at`.
   `call_index` не заменяет календарное время. Запрос со временем раньше
   уже сохранённого наблюдения не читает эту запись и не заменяет её.
5. Явное локальное время принятия и признаки нового эпизода («снова»,
   «повторно», «заново», «новая заявка») имеют приоритет. Несогласованные
   даты принятия одной заявки внутри звонка не объединяются.
6. Переносимая дата не может быть позже звонка или `valid_to`.
   Несовместимые часовые пояса оставляются без переноса.
7. Журнал сохраняет исходный звонок и время наблюдения. Память ограничена
   10 000 записями, предел задаётся `TEMPORAL_SERIES_MAX_ENTRIES`.
   Прогрев в `benchmark.py` и `predict.py` очищает память до измерения.

Повтор последнего запроса сохраняет уже перенесённую дату, если её исходный
звонок строго раньше текущего. Другой звонок с тем же временем историю
не читает. Повторы старого запроса после более нового наблюдения воздерживаются.

Память хранится в одном процессе и не сохраняется после перезапуска.
Для последовательных HTTP-звонков одной серии нужен один worker.
Несколько независимых workers не разделяют историю. Конкурентные запросы,
пришедшие не по времени, могут получить меньше переносов; подмешивания будущей
записи при этом нет. Это не доказательство правильности любой модельной даты:
ошибочная дата первого наблюдения тоже может распространиться дальше.

## Экспериментальный `binding`

`src/temporal_binding.py` связывает явное время со статусом внутри части
реплики, допускает отдельные начала и окончания и короткое подтверждение
предыдущей реплики. Например, «позавчера приняли, а вчера перевели в работу»
содержит два события, а «со вторника до пятницы» — две границы.

Разбор не читает следующие реплики. Для короткого «да, верно» проверяются
только две предыдущие реплики с единственным подходящим статусом. Исходный
`source.turn_idx` не меняется; действительная реплика с датой записывается
в журнал свидетельств. При разных объектах, номерах заявок, противоречащих
датах, вопросе без подтверждения и конфликте интервала правило воздерживается.
Наблюдение «ещё вчера была принята» не считается доказательством начала,
а закрытие заявки не закрывает автоматически статус «выполнена».

Для остальных атрибутов сохранены правила `task`. Нового решения по Q03/Q10
в этот режим не добавляли. Разбор регулярными выражениями не является полным
пониманием речи; ASR-ошибки, границы событий и местоимения остаются ограничениями.

идеальных дат с результатом правил — только диагностика самих правил, а не
метрика извлечения. Разделение аккаунтов по SHA256 modulo 5 дало для нового

Часть примеров полного train читалась при разработке: выделенная часть
не является слепым тестом. После фиксации правил коммитом `4680bd6`

После val добавлена защита повтора последнего HTTP-запроса (`08d67fa`),
проверенная отдельным искусственным примером. Повторная обработка полного val
дала побайтно те же предсказания и журналы для обоих вариантов с историей.

## Как команде проверить вторую модель без GPU

Из корня репозитория в подготовленном окружении. `TEMPORAL_PRED` должен указывать
на сохранённый JSONL второй модели. Каталог запуска должен быть новым.
Все следующие команды работают на CPU; исходные предсказания не переписываются.

```bash
TEMPORAL_PRED=out/json-constrained-continue-002-full-001/predictions.jsonl
TEMPORAL_RUN=out/temporal-next-001

python src/postprocess_dates.py --input data/organizer/val.jsonl --pred "$TEMPORAL_PRED" --mode off --deduplicate --output-dir "$TEMPORAL_RUN/control"
python src/postprocess_dates.py --input data/organizer/val.jsonl --pred "$TEMPORAL_RUN/control/predictions.jsonl" --mode task --output-dir "$TEMPORAL_RUN/task"
python src/postprocess_dates.py --input data/organizer/val.jsonl --pred "$TEMPORAL_RUN/control/predictions.jsonl" --mode task --allow-series-history --output-dir "$TEMPORAL_RUN/task-history"
python src/postprocess_dates.py --input data/organizer/val.jsonl --pred "$TEMPORAL_RUN/control/predictions.jsonl" --mode binding --output-dir "$TEMPORAL_RUN/binding"
python src/postprocess_dates.py --input data/organizer/val.jsonl --pred "$TEMPORAL_RUN/control/predictions.jsonl" --mode binding --allow-series-history --output-dir "$TEMPORAL_RUN/binding-history"

python src/compare_temporal.py --gold data/organizer/val.jsonl --before "$TEMPORAL_RUN/control/predictions.jsonl" --after "$TEMPORAL_RUN/task/predictions.jsonl" --output-dir "$TEMPORAL_RUN/task-vs-control"
python src/compare_temporal.py --gold data/organizer/val.jsonl --before "$TEMPORAL_RUN/task/predictions.jsonl" --after "$TEMPORAL_RUN/task-history/predictions.jsonl" --output-dir "$TEMPORAL_RUN/history-vs-task"
python src/compare_temporal.py --gold data/organizer/val.jsonl --before "$TEMPORAL_RUN/task/predictions.jsonl" --after "$TEMPORAL_RUN/binding/predictions.jsonl" --output-dir "$TEMPORAL_RUN/binding-vs-task"
python src/compare_temporal.py --gold data/organizer/val.jsonl --before "$TEMPORAL_RUN/task-history/predictions.jsonl" --after "$TEMPORAL_RUN/binding-history/predictions.jsonl" --output-dir "$TEMPORAL_RUN/binding-history-vs-task-history"
```

На этом Mac вместо `python` доступен `../MWS/.venv/bin/python`.
Оценка получает gold отдельной командой. Правила получают только `CallInput`,
прошлые предсказания и текущие предсказанные факты.

## Как включить на сервере

После отдельной проверки второй модели, перед запуском сервиса или benchmark:

```bash
export TEMPORAL_NORMALIZATION=task
export TEMPORAL_SERIES_HISTORY=1
export TEMPORAL_SERIES_MAX_ENTRIES=10000
# Эксперимент вместо task: TEMPORAL_NORMALIZATION=binding
```

Для HTTP используйте прежнюю команду запуска, **один worker**, один процесс
на последовательность запросов; перед новым независимым прогоном перезапустите
сервис. `/health` показывает режим, включённую историю и её предел.
Входной `series.account_id` и идентификатор заявки должны быть стабильны.
Отсутствующие идентификаторы не достраиваются по эталонам.

`benchmark.py` записывает флаг истории и предел памяти в `report.json`,
решения — в `calls.jsonl`. Для контрольного запуска задайте
`TEMPORAL_SERIES_HISTORY=0`; чтобы отключить и даты, задайте также
`TEMPORAL_NORMALIZATION=off`. Изменение переменных требует нового процесса.
