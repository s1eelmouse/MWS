# Календарь и детерминированная обработка

Готовые компоненты работают на CPU без загрузки модели. Они не меняют обучающий
prompt, схему фактов и подпись существующего адаптера. Новое обучение не требуется.

## Что реализовано

| Компонент | Файл | Поведение |
|---|---|---|
| Календарь | `src/temporal.py` | Относительные дни, числовые сроки в днях/неделях/часах/минутах, явные ISO/числовые/словесные даты, дни недели с направлением, периоды недель/месяцев, время суток |
| Привязка к фактам | `src/temporal.py` | Режим `task` (по умолчанию): явное время из реплики, иначе дата звонка для `action`; режим `conservative` — прежний узкий набор |
| Серии звонков | `src/postprocess_dates.py` | В пакетном режиме переносит дату «принята» внутри одного `account_id`; истории разных аккаунтов не смешиваются |
| Каталог | `src/catalog_normalization.py` | Только однозначное точное совпадение после нормализации регистра, пробелов и оформления; необязательные явно заданные алиасы |
| Говорящий | `src/prediction.py` | Источник — диаризация исходной реплики; прежнее поведение сохранено |
| Дубли | `src/prediction.py` | Удаление только полных совпадений; прежнее поведение сохранено |
| Обработка файлов | `src/postprocess_dates.py` | Новый файл предсказаний, журнал решений и манифест; исходные результаты не перезаписываются |
| Сравнение дат | `src/compare_temporal.py` | Проверяет неизменность фактов/порядка/других полей, считает исправления и регрессии официальным оценщиком |

## Режим `task` — что и почему

`TEMPORAL_NORMALIZATION=task` — режим по умолчанию. Он не меняет prompt, схему,
подпись адаптера и не требует обучения. Правила читают только вход звонка и
предсказанный факт:

| Атрибут | Правило |
|---|---|
| `ticket_status` | В части реплики, где назван статус, ищется явное время: «сегодня/сейчас», «вчера», «N дней назад», «с <день недели>». Если время стоит после «до», меняется `valid_to`, иначе `valid_from` |
| `action` | Если в части реплики с действием есть явное прошедшее время, берётся оно; иначе `valid_from` = `started_at` (время заявления, не события) |
| `agreement` | Явное будущее время («завтра», «через N дней/недель», «в <день недели>») задаёт дату события |
| `service_state`, `tariff` | Не меняются: историческое начало из текста не выводится |

Несколько разных дат в одной части реплики, отрицательная полярность, неверная
дата модели и конфликт с уже закрытым интервалом оставляют факт без изменения.
Замена невозможной даты на «похожую» не выполняется; её по-прежнему обнуляет
`sanitize_interval`.

В пакетном режиме (`benchmark.py` автоматически или `postprocess_dates.py
--mode task`) дата статуса «принята» переносится из предыдущего звонка той же
серии и того же `account_id`. Это даёт +0.024 `temporal_recall` на полном val,
но требует обработки серии целиком; HTTP-сервис, который видит один звонок,
получает только пофактные правила. Benchmark пишет `temporal-audit.jsonl` и
поле `temporal_postprocess` в `report.json`.

## Принципы календаря

- Единственная точка отсчёта — `started_at` текущего звонка. Системные часы не используются.
- Сохраняется часовой пояс, если он указан во входе.
- Високосность и границы месяца/года рассчитываются стандартным календарём.
- Невозможные даты не заменяются ближайшими существующими датами.
- «На прошлой неделе» возвращает диапазон календарной ISO-недели, а не выдуманный
  конкретный день. Это не утверждение о политике разметки организаторов.
- «В прошлом месяце» возвращает границы месяца. `shift_calendar_months` сдвигает
  календарный месяц с сохранением числа; при несуществующем числе выбрасывает
  ошибку, а не молча обрезает его.
- Год в неполной дате и день недели требуют направления `past`/`future`; совпадение
  дня недели с днём звонка оставляется неоднозначным.
- «После двух» без дополнительных условий неоднозначно. Публичный API позволяет
  явно выбрать `daytime_hours=True`, тогда это нижняя граница после 14:00.
  Автоматическая привязка фактов эту конвенцию не включает.
- У выражения есть исходный фрагмент, символьные границы, точность, отношение
  (`at`/`after`/`before`/`by`/`period`), правило и причина неопределённости.

Пример программного использования при `PYTHONPATH=src`:

```python
from temporal import extract_time_expressions

items = extract_time_expressions("вчера", "2026-03-01T12:00:00+03:00")
assert items[0].start == "2026-02-28T00:00:00+03:00"

items = extract_time_expressions(
    "завтра после двух", "2026-03-01T12:00:00", daytime_hours=True
)
assert items[0].start == "2026-03-02T14:00:00"
assert items[0].relation == "after"
```

## Что автоматически не угадывается

Неизвестное историческое начало `service_state`/`tariff`, «на прошлой неделе» без
конкретного дня, включительность окончания «до ...», несколько времён в одной части
реплики, вопрос/гипотеза/отрицательный факт и одинаковое свидетельство для разных
объектов. Такие случаи остаются без изменения и получают причину в журнале.

В `conservative` режиме `action` и `agreement` вообще не меняются: корпус смешивает
время события и время заявления, и прежнее правило не пыталось их различить.
`task` использует конвенцию, измеренную на train: `action` без явного времени —
время звонка, `agreement` с явным будущим временем — дата события.

Правила работают только с исходной репликой указанного `source.turn_idx`. Они не
переносят источник на другую реплику по похожести слов и не используют историю
аккаунта. Короткое подтверждение без собственного времени пока не разрешается
автоматически через предыдущую реплику. Это ограничение привязки, а не календаря.

Значения `polarity` не переворачиваются по наличию слова «не»: фраза «перезагрузил —
не помогло» по-прежнему означает выполненное действие. Семантика подтверждения и
отрицания остаётся задачей извлечения. Старые состояния не закрываются массово.

## Запуск без GPU

Все команды из корня репозитория, в подготовленном Python-окружении. На этом Mac
доступен также интерпретатор соседней копии: `../MWS/.venv/bin/python` вместо `python`.

```bash
python src/postprocess_dates.py --input data/organizer/val.jsonl --pred out/json-constrained-4090-baseline-001-full-001/predictions.jsonl --output-dir out/time-calendar-001
python src/compare_temporal.py --gold data/organizer/val.jsonl --before out/json-constrained-4090-baseline-001-full-001/predictions.jsonl --after out/time-calendar-001/predictions.jsonl --output-dir out/time-calendar-001-comparison
```

Имена результатов должны быть новыми. Результат:

```text
out/time-calendar-001/
  predictions.jsonl  # копия предсказаний с разрешёнными правками
  audit.jsonl        # решения по фактам, свидетельства, старое/новое значение
  manifest.json     # режим, счётчики, время, хеши данных и исходников
out/time-calendar-001-comparison/
  comparison.json       # официальные метрики до/после и переходы
  changed-matches.jsonl # изменённые сопоставленные факты: исправлен/испорчен/ещё неверен
```

`--input` может быть выданным JSONL с разметкой, но на границе вызывается `as_call`:
до правил доходят только поля `CallInput`, без эталонных фактов. Оценка читает gold
отдельной командой. Правила не получают путь к gold и не выбирают правки по нему.

Независимые дополнительные операции, которые следует оценивать отдельно:

```bash
python src/postprocess_dates.py --input data/organizer/val.jsonl --pred out/json-constrained-4090-baseline-001-full-001/predictions.jsonl --output-dir out/catalog-001 --mode off --catalog case_data/catalog.json
python src/postprocess_dates.py --input data/organizer/val.jsonl --pred out/json-constrained-4090-baseline-001-full-001/predictions.jsonl --output-dir out/dedup-001 --mode off --deduplicate --speaker-from-source
```

После изменения каталога, говорящего или количества фактов используйте обычный
`src/eval.py`, а не сравнение, которое требует изменения только дат.

## Подключение к инференсу

`TEMPORAL_NORMALIZATION=task` включён по умолчанию. Отключение или возврат к
прежнему узкому набору:

```bash
export TEMPORAL_NORMALIZATION=off        # только даты модели
export TEMPORAL_NORMALIZATION=conservative  # прежние 7 исправлений на val
# Необязательно, отдельный эксперимент:
export CATALOG_PATH=data/organizer/catalog.json
```

В PowerShell: `$env:TEMPORAL_NORMALIZATION = "task"` (или `off`/`conservative`).
После этого запустите обычный benchmark с существующей merged-моделью в новый
каталог. `report.json` сохраняет режим и хеш каталога, а `calls.jsonl` —
`temporal_decisions` и числовые счётчики нормализации. Это рекомендуемый путь
проверки на сервере с журналом; обычный HTTP-ответ сохраняет прежнюю схему фактов.

Восстановление невозможной даты выполняется до строгой проверки `Facts`; если
однозначных свидетельств нет, остаётся прежняя обработка некорректных дат.
Для отключения: `TEMPORAL_NORMALIZATION=off`, удалить/обнулить `CATALOG_PATH`.

## Проверка на полном val — 14.11.2026

Полный val — 383 звонка, официальный оценщик. `task` меняет только даты, поэтому
precision, recall, grounding и порядок фактов не меняются; `state_accuracy`
пересчитывается по новым датам.

### Baseline `4090-baseline-001` + constrained + dedup

| Вариант | Pred | Совпало | Precision | Recall | Temporal | State |
|---|---:|---:|---:|---:|---:|---:|
| Без правил | 1989 | 721 | 0.3625 | 0.3908 | 0.3315 | 0.3467 |
| `conservative` | 1989 | 721 | 0.3625 | 0.3908 | 0.3398 | 0.3435 |
| `task`, на звонок | 1989 | 721 | 0.3625 | 0.3908 | 0.3856 | 0.3467 |
| `task` + серии, пакет | 1989 | 721 | 0.3625 | 0.3908 | **0.3994** | 0.3467 |

### Основная модель `4090-continue-002` (constrained, 0 отказов)

| Вариант | Pred | Совпало | Precision | Recall | Temporal | State |
|---|---:|---:|---:|---:|---:|---:|
| Без правил | 1896 | 760 | 0.4008 | 0.4119 | 0.3566 | 0.3852 |
| `task`, на звонок | 1896 | 760 | 0.4008 | 0.4119 | 0.3947 | 0.3852 |
| `task` + серии, пакет | 1896 | 760 | 0.4008 | 0.4119 | **0.4184** | 0.3852 |

`task` изменил 446 полей дат; перенос внутри серий — ещё 37. Официальное
сравнение: **67 исправленных пар дат и 20 регрессий** у `continue-002`
(у baseline 64 и 15). Отсечение кейса `temporal_recall` < 0.371 пройдено в обоих
вариантах. Пакетный результат 0.4184 отличается от базы 0.4205 на 0.0021 —
в пределах допуска 0.02; пофактный режим HTTP-сервиса (0.3947) проходит
отсечение, но отстаёт от базы на 0.0258. `state_accuracy` 0.3852 выше базы 0.3194.

### Переносимость правил

Правила настраивались по явным временным конструкциям, а не по номерам звонков.
На train (3 926 звонков, 18 475 фактов) точность привязки к эталонной дате:
`ticket_status` 0.768, `action` 0.854, `agreement` 0.383. Слабейшее место —
`agreement`: корпус смешивает дату события и дату заявления, и без цитаты-источника
их не различить. Поэтому в отчёте режим `task` описан как измеренная эвристика,
а не как гарантия semantics.

На шумном val (`--level 0.15 --seed 42`, baseline) `task` поднял
`temporal_recall` 0.3194 → 0.3657 и `state_accuracy` 0.3114 → 0.3162. Это
стресс-тест, не замена скрытому adversarial-срезу.

До val правила проверялись на train и искусственных случаях. Проверка идеальной
разметки train показывает неоднородность дат: часть эталонных `ticket_status`
не выводится из текста. Поэтому потолок `temporal_recall` ограничен не только
календарём, но и самой разметкой.

Результаты в `out/time-constrained-audit-001`, `out/time-calendar-001`,
`out/time-calendar-001-comparison`, `out/time-catalog-001`. Финальная версия после
проверок пределов datetime сохранена в `out/time-calendar-002`; её предсказания
побайтно совпадают с оценённой первой версией. Проверка соответствия и итоговые
метрики — `out/time-final-verification-001.json`. Результаты локальные и в Git
не добавляются. Веса и исходные предсказания не изменялись, обучение не запускалось.

## Проверки

```bash
python -m unittest discover -s tests -p 'test_*.py'
python -m compileall -q src tests
```

Проверяются високосность, границы месяца/года/диапазона datetime, часовой пояс,
направление дня недели, точность времени, неизвестные даты, независимость объектов,
разные события/границы, восстановление до валидации, отсутствие gold в правилах,
неизменность других полей и обнаружение регрессий. Реальная XGrammar/GPU-проверка
в этой CPU-среде не заменяется подставными тестами.

Итог после добавления `task`, серий и пакетного шага в benchmark: **144 теста**,
в CPU-окружении 139 прошли, 5 пропущены; на сервере с torch/XGrammar проходят
все. `compileall` и `git diff --check` прошли. Тесты `tests/test_temporal_task.py` проверяют явные
даты, `до` как конец интервала, конвенцию `action`, будущее время `agreement`,
защиту интервала, восстановление невозможной даты и перенос только внутри своего
`account_id`.
