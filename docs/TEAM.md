# Совместная работа команды

## Общая схема

У каждого участника — своя локальная копия приватного репозитория и доступ на GitHub. Работа ведётся в отдельных ветках. В main объединяем проверенные изменения через pull request; основную интеграцию координирует один участник.

Перед параллельной работой согласовать пример входа/выхода и границы модулей. Изменения schema.py затрагивают обучение, CLI, API и оценку, поэтому о них нужно сообщать всей команде заранее.

## Начало задачи

Пример для чистой локальной рабочей копии:

```text
git status
git switch main
git pull --ff-only
git switch -c docs/case-readme
```

Если есть незавершённые изменения, сначала сохранить их в своей ветке. При ошибке pull или конфликте не использовать reset --hard и принудительную отправку в main; сначала разобраться с участником, чьи изменения пересекаются.

## Отправка изменений

```text
git diff
git add README.md docs/PLAN.md docs/TEAM.md docs/LEGACY_STARTER.md
git diff --cached
git commit -m "docs: align documentation with hackathon case"
git push -u origin docs/case-readme
```

Имена ветки и файлов выше — пример для документации. Для другой задачи добавить только её файлы, затем открыть pull request на GitHub. Эта инструкция сама не создаёт commit и не отправляет изменения.

В pull request указать:

- Что изменено и какую часть кейса закрывает.
- Как проверено, включая ограничения проверки.
- Изменился ли общий контракт и что должны обновить остальные участники.

После объединения участники обновляют свои копии main. Длительные ветки согласовывают обновление с ответственным за интеграцию.

## Предлагаемое распределение

| Зона | Ответственность |
| --- | --- |
| Контракт и данные | Новая схема, сериализация реплик, примеры входа/выхода |
| Обучение | LoRA/QLoRA, seed, сохранение запусков, merge |
| Предметная логика | Даты, каталог, подтверждения, интервалы состояний |
| Оценка | Официальный оценщик, отчёт ошибок, ресурсные измерения |
| Сервис и демонстрация | API, Docker, интерфейс показа и сборка презентации |

Это зоны координации, а не запрет помогать друг другу. Проверять совместимость по одному общему звонку после каждого изменения контракта.

## Данные и результаты

- Оригинальный пакет хранить рядом с repository, а не редактировать поверх исходников организаторов.
- В Git добавлять код, инструкции и разрешённые небольшие примеры. Закрытые данные, ключи и большие веса не добавлять.
- `.gitignore` уже исключает data/* кроме sample.jsonl, out/, .venv/ и .env. Файлы в других каталогах автоматически не защищены этим правилом.
- Результаты каждого запуска сохранять отдельно с именем модели, конфигурацией и показателями. Не перезаписывать общий out/adapter несколькими экспериментами.
- Общий GPU-сервер согласовывать: два одновременных обучения могут мешать друг другу и портить ресурсные замеры.
- Секреты не писать в README, примеры команд, commit или скриншоты.

## Проверка перед объединением

Для документации: ссылки, команды и соответствие текущему состоянию кода. Для программных изменений: подходящие проверки затронутой логики и общий пример звонка. Существующие 25 тестов не покрывают новый официальный формат; их успешность не заменяет проверку адаптации.
