# CompactFactExtraction — Инноглобалхак

Компактный экстрактор фактов из русскоязычных диалогов технической поддержки с ошибками распознавания речи. Цель — восстановить факты, время их действия и актуальное состояние объектов, сохранив ссылку на реплики-источники.

## Текущее состояние

**Репозиторий находится в процессе адаптации к выданному кейсу.** Сейчас код работает со старым учебным форматом: одна карточка обращения с полями `product`, `category`, `problem`, `request`, `ids`, `error_code`, `urgency`.

Официальный формат другой: звонок содержит `call_id`, `started_at`, `turns` и список `facts`. Поэтому текущие `train.py`, `predict.py`, `serve.py`, `check_data.py` и `eval.py` ещё нельзя использовать с официальными данными без адаптации.

| Уже есть | Нужно реализовать |
| --- | --- |
| Каркас LoRA/QLoRA и слияние адаптера | Подготовка официальных диалогов и целевых ответов |
| Загрузка модели и пакетный инференс | Список фактов с объектами, полярностью и источниками |
| FastAPI и очередь запросов | Новый контракт API и Docker |
| Измерение задержки и выгрузка ошибок | Официальные метрики, память, CPU/GPU и режимы эффективности |
| 25 тестов старой схемы и метрики | Проверки дат, состояний, подтверждений и нового формата |

Проверка 13.11.2026: 25 существующих тестов прошли. Это проверка прежней задачи; качество на официальном корпусе и работа нового контракта пока не подтверждены. Обучение и GPU-инференс в ходе этой проверки не запускались.

## Подход

Первый кандидат — **Qwen3-0.6B с отключённым thinking** и дообучением на выданном train. Версию 1.7B рассматриваем после анализа ошибок 0.6B и подтверждения допустимости размера организаторами.

Это принятое направление разработки, а не уже реализованная конфигурация: в `src/config.py` пока остаётся прежнее значение `Qwen/Qwen3-1.7B`. Для экспериментов задавайте модель явно и используйте отдельные каталоги результатов.

Модель должна извлекать смысл и источники. Вычисление относительных дат, нормализацию по каталогу и обновление состояний планируем вынести в проверяемые компоненты.

```text
Звонок с датой и репликами
    -> модель: объекты, атрибуты, значения, временные выражения, источники
    -> проверка результата, нормализация дат и каталога
    -> обновление состояний
    -> факты в официальной схеме
```

Точное представление неизвестных дат, значений вне каталога и источников подтверждения уточняется у ментора. Эталонные `facts` не должны попадать во вход модели ни при обучении, ни при проверке.

## Данные

Рекомендуем хранить оригинальный пакет отдельно от исходников:


В проверенной версии пакета: train — 3 926 звонков / 18 475 фактов; val — 383 звонка / 1 845 фактов. При обновлении пакета эти числа нужно перепроверить.

Правила работы:

- Использовать готовые train/val организаторов. Не объединять и не переразбивать их старым `split.py`.
- Если нужна внутренняя отложенная часть train, разделять по аккаунтам/сериям звонков.
- Оригиналы хранить неизменными. Производные данные и диагностические замечания сохранять отдельно.
- Поля `idx` и `speaker` сохранять. Даты вычислять относительно `started_at`.
- Дополнительную разметку учителем отложить до рабочего процесса на готовом train и уточнения допустимых источников данных.
- Не добавлять закрытые данные и веса в Git. Текущий `.gitignore` исключает `data/*` кроме учебного примера, `out/`, `.venv/` и `.env`.

## Что можно проверить сейчас

Все команды ниже выполняются из корня репозитория. Для первого запуска рекомендуем Python 3.12. Обучение планируем выполнять под Linux; Windows можно использовать для разработки и проверок без GPU.

### Проверки существующего кода без GPU

Для этих проверок достаточно Pydantic; устанавливать весь обучающий стек необязательно.

```text
uv venv --python 3.12
uv pip install "pydantic>=2.7"
```

Активировать окружение:

```powershell
# Windows PowerShell
.venv\Scripts\Activate.ps1
```

```bash
# Linux
source .venv/bin/activate
```

После активации:

```text
python -m unittest discover -s tests -v
python src/check_data.py data/sample.jsonl
```

Эти команды проверяют старую карточку обращения. `check_data.py` пока не является валидатором официального корпуса.

### Воспроизведение официального baseline

Если пакет лежит по схеме выше, эти команды работают независимо от адаптации `src/` и требуют только Python:

```text
python "../Данные кейса/case_metrics.py" "../Данные кейса/val.jsonl" "../Данные кейса/baseline_pred.jsonl"
python "../Данные кейса/case_metrics.py" "../Данные кейса/val.jsonl" "../Данные кейса/val.jsonl"
```

Вторая команда — диагностическое сравнение эталона с самим собой. Она не является оценкой нашей модели.

| Метрика | Приложенный отчёт baseline | Пересчёт 13.11.2026 |
| --- | ---: | ---: |
| fact_precision | 0.2074 | 0.2189 |
| fact_recall | 0.2358 | 0.2488 |
| temporal_recall | 0.4161 | 0.4205 |
| state_accuracy | 0.3483 | 0.3194 |
| grounding_turn | 0.6759 | 0.6906 |

Известные вопросы к пакету:

- Эталон против себя получает `state_accuracy = 0.8957`: выбор предсказанного состояния в текущем оценщике не учитывает объект.
- `temporal_recall` проверяет даты только среди уже сопоставленных фактов; читать её нужно вместе с общей полнотой.
- Есть расхождения между каталогом, свободными значениями в разметке и описанием дат.

Официальную версию оценщика и исходные числа нужно подтвердить у ментора. Самостоятельно изменённые метрики нельзя выдавать за официальные.

## Подготовка окружения для обучения

После активации отдельного окружения обучения установить совместимую с GPU сборку PyTorch и зависимости `requirements.txt`. Для RTX 4060/A10 исходная команда установки:

```text
uv pip install torch --torch-backend=auto
uv pip install -r requirements.txt
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
```

Эта инструкция не означает, что любая новая комбинация версий уже проверена. Для V100 требуется отдельно подобрать совместимую сборку PyTorch/CUDA. После успешного короткого запуска сохранить версии:

```text
uv pip freeze > requirements.lock.txt
```

`requirements.lock.txt` здесь — снимок проверенного окружения для данной платформы. Оборудование и ОС также нужно записать. Сейчас такого зафиксированного окружения в репозитории нет.

Основное обучение на официальном корпусе запускать после этапов 1–3 из [плана](docs/PLAN.md). Прежние команды обучения сохранены в архивной инструкции с пометкой о старом формате.

## Текущие ограничения

- Вход обрезается до 3 000 символов, а полный эталонный ответ сохраняется. Это нужно исправить до обучения на диалогах.
- Ответ ограничен 256 новыми токенами; достаточность для новой схемы не измерена.
- Старые поля должны быть цитатами. В новой задаче нормализованное значение и цитата-источник — разные сущности.
- HTTP-ответ с `error/raw` не означает корректный ответ по схеме фактов.
- В CPU-ветке используется float32; оптимизированный CPU-режим пока не подготовлен.
- Dockerfile, обработка временных состояний и адаптер официального формата пока отсутствуют.
- vLLM и MCP — дополнительные направления после готовности основного процесса.

## Что подготовить к сдаче

- Обученные веса/адаптер с конфигурацией, версиями и кодом обучения.
- Docker с согласованным HTTP-контрактом и инструкцией запуска.
- Официальные показатели качества и разбор ошибок по типам фактов.
- Замеры памяти, задержки и пропускной способности на CPU и GPU.
- Кривую «ресурсы × качество» минимум в трёх точках по согласованным правилам.
- Демонстрацию и презентацию. Описание кейса разрешает показ вживую или видео; оборудование и порядок проверки уточняем у организаторов.

## Как интерпретировать прежние замеры

Замеры автора на 32 учебных обращениях сохранены в [архиве](docs/LEGACY_STARTER.md). Они показывают историю проверки каркаса, но не качество и скорость на официальном корпусе.

Зависимость времени от размера модели, длины входа, длины ответа, размера пачки и backend нужно измерить заново. Совпадение отдельных ответов после слияния или ускорения не доказывает эквивалентность на всём корпусе.
